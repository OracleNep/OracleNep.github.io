01. JavaSecAtlas V1.2：我没有继续造一个低配 SAST

最初的定位很具体：给 Java / Spring 项目做一个白盒审计辅助工具，把项目识别、路由提取、权限注解提取、启发式规则扫描和报告生成串起来。

做到 V1.2 的时候卡住了。继续沿着“自己写更多规则”往下堆，最后大概率会变成一个低配版 SAST。这就很尴尬——安全圈并不缺工具。

Semgrep 规则好写，适合快速做模式匹配和工程化落地；CodeQL 适合做数据流、调用链和变体分析；Fortify 那类商业产品更偏企业治理、规则库和合规流程。一个个人项目，既没有规则库的积累，也没有专门的人去维护规则质量，硬碰这些方向没什么胜算。

所以 V1.2 换了个问题：JavaSecAtlas 不跟成熟 SAST 比扫描能力，把它们的结果接进来，当成 Java / Spring 审计流程里的一段。

中间缺的那一段

扫描器输出的是 finding，审计最后要的是能复核、能解释、能写进报告的线索。两头之间隔着一层很实在的工作：

  • 这个点属于哪个 Controller？
  • 对应哪个路由？
  • 有没有权限注解？
  • 参数是不是用户可控？
  • 它是真实风险还是误报？
  • 修复建议怎么写才不空？

这些问题扫描器不回答，报告模板也回答不了。JavaSecAtlas 想补的就是这一层：把扫描结果放回 Java 项目的上下文里，再往审计线索、人工复核和报告交付推。

V1.2 实际做了什么

python -m javasecatlas scan \
  -t examples/spring-vuln-demo \
  -o reports \
  -f all \
  --import-sarif semgrep.sarif \
  --import-sarif codeql.sarif

跑起来是这个顺序：先执行自己的扫描逻辑，再导入外部 SARIF，最后统一出 JSON、Markdown、HTML、SARIF 四种报告。

别把定位说大

我不会说 JavaSecAtlas 比 Semgrep、CodeQL、Fortify 强。这种话既不准，也容易被真正做过 SAST 的人一眼看穿。能说清楚的是分工：Semgrep / CodeQL 负责发现候选 finding，JavaSecAtlas 负责导入、归一化、补上下文、组织报告，Agent 只做辅助复核和表达整理。谁是裁判这件事，不因为多了个 Agent 就变了。

02. SARIF 导入：把外部扫描结果接进来

SARIF 是静态分析结果的通用交换格式。对 JavaSecAtlas 来说，支持它的实际好处很直接：能接住 Semgrep、CodeQL 已经跑出来的结果，不必要求用户只用自家的规则。

V1.2 新增的导入模块只有一个核心函数：

load_sarif_findings(path: Path) -> list[Finding]

做的事不复杂：读 SARIF，把外面的 result 转成自己的 Finding。转完之后，报告、过滤、Agent 复核就能用同一套结构处理，不用为每个工具写一遍分支。

字段怎么映射

SARIF 字段JavaSecAtlas 字段说明
ruleIdrule_id加上外部来源前缀，例如 external.semgrep...
message.textmessage保留工具原始描述，方便回看
artifactLocation.urifile记录命中文件路径
region.startLineline记录起始行
region.startColumncolumn记录起始列
result.levelseverity做基础严重等级映射
rule.properties.tagstags保留 CWE、语言、规则类别等信息

导进来长什么样

rule_id: external.semgrep.java.lang.security.audit.crypto.use-of-md5.use-of-md5
severity: medium
file: src/main/java/demo/WeakCrypto.java
line: 12
column: 20
tags: external-sarif, tool:semgrep, CWE-328

这一步解决的问题很窄：以前只能处理自己的规则结果，现在外部结果也进得来。关联、去重、排序、复核，都排在它后面。

顺序反了很容易出问题。我见过不少工具先做“智能优先级排序”，数据源却只有一家扫描器的输出，排出来的东西没人信。先让数据进来，再谈怎么排。

03. 下一步：把 finding 绑到 Spring 路由上

只做导入的话，JavaSecAtlas 跟一个 SARIF 查看器没多大区别。真正想拉开差距的地方，是把 finding 放回 Java / Spring 项目的入口上。

真实审计里，看到一个 sink 不会马上下结论。下一步通常是往上追：这个代码点被哪个 Controller 调到了？URL 是什么？有没有权限注解？参数能不能从请求一路传到危险函数？这些问题答完，才知道要不要继续。

希望生成的线索长什么样

风险类型：路径穿越候选点
入口路由：POST /api/file/read
Controller：FileController#readFile
权限情况：未发现方法级权限注解
可控参数：filename
命中来源：JavaSecAtlas heuristic + Semgrep SARIF
复核建议：检查 filename 是否进入 Path.resolve / File 构造逻辑，确认是否有目录白名单、路径归一化和越权读取限制

实现上的五步

  1. 提取 Spring Controller、方法、路由和权限注解；
  2. 记录每个方法的大致文件路径和行号范围；
  3. 把 finding 的文件和行号落到对应方法附近；
  4. 把路由、HTTP 方法、权限注解补回 finding；
  5. 报告按“入口接口”组织，而不是按规则 ID 排。

这套东西不完美。行号落在方法附近靠的是范围匹配，嵌套类、内部类、多模块同名文件都会出偏差。但作为第一版 correlation 够用——先把 60 分的上下文补上，再谈跨函数调用链和数据流。

04. Agent 复核：让 AI 干适合它干的活

“把整份代码丢给大模型，让它自动审计”这种说法我不太认同。听起来很爽，实际很容易变成幻觉生成器——尤其在没有上下文的时候，它给出的结论往往比人更自信。

规则扫描 / SARIF 导入
        ↓
路由、权限、依赖、代码片段上下文整理
        ↓
Agent 辅助判断：可控参数、利用条件、误报可能、修复建议
        ↓
人工复核
        ↓
报告输出

它可以做

  • 根据命中点和上下文，解释这里为什么可能有风险；
  • 把扫描器的英文描述改写成审计报告里的说法；
  • 列出需要人工确认的条件，比如“参数是否可控”“有没有白名单”；
  • 写修复建议草稿；
  • 把几个工具的 findings 合并成一段能读的复核说明。

它不该做

  • 不该凭空说“这里一定能 RCE”；
  • 不该在没有上下文的情况下编攻击链；
  • 不该替代人工做最终确认；
  • 不该接触未脱敏的业务代码、凭据或真实资产信息。

我不想把 JavaSecAtlas 写成“AI 自动挖洞神器”。更实际的定位是：成熟工具发现候选点，JavaSecAtlas 把候选点整理成人能看的线索，Agent 负责解释和草稿，最后一步还是人。

如果继续迭代，我会先做 finding correlation，而不是先堆 AI 功能。上下文没整理干净的时候，Agent 接得越深，说胡话的概率越高——这一点和 prtseek 那边踩过的坑是一样的。
