JavaSecAtlas V1.2 SAST 编排 项目复盘

01. JavaSecAtlas V1.2：我没有继续造一个低配 SAST

JavaSecAtlas 一开始的想法很简单：做一个面向 Java / Spring 项目的白盒审计辅助工具，把项目识别、路由提取、权限注解提取、启发式规则扫描和报告生成这些事情串起来。

但做到 V1.2 的时候，我重新想了一下这个项目到底应该往哪走。如果继续沿着“自己写更多扫描规则”的方向堆下去，最后大概率会变成一个低配版 SAST。这就很尴尬了。

因为安全圈已经有很多成熟工具了。Semgrep 规则好写，适合快速做模式匹配和工程化落地；CodeQL 更适合做深度数据流、调用链和变体分析；Fortify 这类商业 SAST 更偏企业级治理、规则库和合规流程。我一个个人 / 团队实验项目，没必要也不现实去碰瓷这些东西。

V1.2 这版，我没有继续试图“打败” Semgrep 或 CodeQL，而是换了一个方向：JavaSecAtlas 不替代成熟 SAST，而是把它们的结果接进来，作为 Java / Spring 审计工作流的一部分。

为什么这个转向比较重要

扫描器输出的是 finding，但代码审计最后需要的是可以复核、可以解释、可以写进报告的线索。两者之间差了一段很实际的工作：

  • 这个点属于哪个 Controller？
  • 对应哪个路由？
  • 有没有权限注解？
  • 参数是不是用户可控？
  • 这个 finding 是真实风险还是误报？
  • 修复建议怎么写才不空？

JavaSecAtlas 后续要补的就是这段中间层。它不是“再造一个扫描器”，而是想把扫描结果放进 Java 项目的上下文里，再往审计线索、人工复核和报告交付方向推进。

V1.2 做了什么

V1.2 新增了外部 SARIF 导入能力。现在可以这样使用：

python -m javasecatlas scan \
  -t examples/spring-vuln-demo \
  -o reports \
  -f all \
  --import-sarif semgrep.sarif \
  --import-sarif codeql.sarif

这个流程里，JavaSecAtlas 会先执行自己的扫描逻辑，然后导入外部 SARIF findings，最后统一进入 JSON、Markdown、HTML、SARIF 报告输出流程。

我想保留的边界感

我不会说 JavaSecAtlas 比 Semgrep、CodeQL、Fortify 更强。这种说法既不准确，也很容易被真正做过 SAST 的人一眼看穿。更合理的说法是：

  • Semgrep / CodeQL 负责发现候选 finding；
  • JavaSecAtlas 负责导入、归一化、上下文整理和报告组织；
  • 后续 Agent 只做辅助复核和表达整理，不负责凭空判断漏洞。

这样项目的定位会更稳，也更接近真实安全工程里的工作方式。

02. SARIF 导入：把外部扫描结果接进来

SARIF 可以理解成静态分析结果的通用交换格式。对 JavaSecAtlas 来说，支持 SARIF 的意义不是“蹭格式”，而是让它能接住 Semgrep、CodeQL 等工具已经发现的结果。

V1.2 里新增了一个导入模块，核心函数是：

load_sarif_findings(path: Path) -> list[Finding]

这个函数做的事情不复杂：读取 SARIF 文件，把外部工具的 result 转成 JavaSecAtlas 自己的 Finding 对象。这样后面的报告、过滤、Agent 复核就可以用同一套数据结构处理。

字段怎么映射

SARIF 字段JavaSecAtlas 字段说明
ruleIdrule_id加上外部来源前缀，例如 external.semgrep...
message.textmessage保留工具原始描述，方便回看
artifactLocation.urifile记录命中文件路径
region.startLineline记录起始行
region.startColumncolumn记录起始列
result.levelseverity做基础严重等级映射
rule.properties.tagstags保留 CWE、语言、规则类别等信息

一个实际例子

比如 Semgrep 扫到一个 MD5 使用点，SARIF 里可能会有这样的信息：

{
  "ruleId": "java.lang.security.audit.crypto.use-of-md5.use-of-md5",
  "level": "warning",
  "message": {
    "text": "Detected MD5 usage."
  },
  "locations": [
    {
      "physicalLocation": {
        "artifactLocation": {
          "uri": "src/main/java/demo/WeakCrypto.java"
        },
        "region": {
          "startLine": 12,
          "startColumn": 20
        }
      }
    }
  ]
}

导入之后，它会被转换成类似这样的 finding：

rule_id: external.semgrep.java.lang.security.audit.crypto.use-of-md5.use-of-md5
severity: medium
file: src/main/java/demo/WeakCrypto.java
line: 12
column: 20
tags: external-sarif, tool:semgrep, CWE-328

这一步解决了什么

它解决的是“外部扫描结果进不来”的问题。以前 JavaSecAtlas 只能处理自己的规则结果，现在可以接收 Semgrep / CodeQL 输出，再统一进入报告流程。这个改动看起来不炫，但很关键：项目开始从一个自写规则工具，往审计工作流编排器靠近。

这一步还没解决什么

V1.2 只是先打通导入链路，还没有做强去重，也没有把每个 finding 精确绑定到 Spring 路由和权限上下文上。如果 JavaSecAtlas 自己扫到一个点，Semgrep 也扫到同一个点，现在可能会出现两条记录。这不是最终形态，但在这个阶段可以接受。

我的理解是：先把数据接进来，再谈关联、去重、优先级排序和复核。顺序反了，项目很容易变成空架子。

03. 下一步：把 finding 绑到 Spring 路由上

如果只是把 Semgrep / CodeQL 的结果导进来，JavaSecAtlas 还只是一个结果聚合器。真正和普通 SARIF 查看器拉开差距的地方，是把 finding 放回 Java / Spring 项目的业务入口里。

真实审计里，我看到一个 sink 并不会马上下结论。更常见的流程是继续追入口：

  • 这个代码点是不是被 Controller 调到了？
  • 对应的 URL 是什么？
  • 是 GET、POST，还是文件上传接口？
  • 有没有 @PreAuthorize、@RequiresPermissions、@SaCheckPermission 这类权限注解？
  • 如果没有显式权限注解，是否还有全局拦截器或网关控制？
  • 参数能不能从 HTTP 请求一路传到危险函数？

我希望后续生成什么样的线索

理想状态下，一个 finding 不应该只是这样：

src/main/java/demo/FileController.java:48
Potential path traversal

而应该尽量整理成这样：

风险类型：路径穿越候选点
入口路由：POST /api/file/read
Controller：FileController#readFile
权限情况：未发现方法级权限注解
可控参数：filename
命中来源：JavaSecAtlas heuristic + Semgrep SARIF
复核建议：检查 filename 是否进入 Path.resolve / File 构造逻辑，确认是否有目录白名单、路径归一化和越权读取限制

这才更接近人工审计时真正有用的东西。

技术上怎么做

我不打算一上来就做很重的数据流。更现实的做法是先做轻量关联：

  1. 提取 Spring Controller、方法、路由和权限注解；
  2. 记录每个方法的大致文件路径和行号范围；
  3. 把 finding 的文件和行号落到对应方法附近；
  4. 把路由、HTTP 方法、权限注解补回 finding；
  5. 在报告里按“入口接口”而不是单纯按“规则 ID”组织结果。

这个方案不完美，但足够作为第一版 correlation。先把 60 分的上下文补起来，再慢慢考虑更复杂的跨函数调用链和数据流。

为什么这件事值得做

因为这一步能把工具从“扫代码”推到“辅助审计”。扫描结果越多，人工越需要排序和上下文。一个没有入口、没有权限、没有业务场景的 finding，很难直接变成报告；但如果它已经带上路由和权限信息，审计人员就能更快判断优先级。

这也是我认为 JavaSecAtlas 后续最该做的方向：不和成熟 SAST 比谁的规则更多，而是把 Java / Spring 审计里的上下文整理好。

04. Agent 复核：让 AI 干适合它干的活

我不太认同“把整份代码丢给大模型，让它自动审计”的说法。这个方向听起来很爽，但实际很容易变成幻觉生成器。AI 可以参与审计，但最好别让它当唯一裁判。

在 JavaSecAtlas 里，我更想让 Agent 做的是复核和表达整理，而不是替代确定性扫描。比较合理的流程是：

规则扫描 / SARIF 导入
        ↓
路由、权限、依赖、代码片段上下文整理
        ↓
Agent 辅助判断：可控参数、利用条件、误报可能、修复建议
        ↓
人工复核
        ↓
报告输出

Agent 可以做什么

  • 根据命中点和上下文，帮忙总结为什么这里可能有风险；
  • 把扫描器的英文描述翻译成更像审计报告的话；
  • 提示需要人工确认的条件，比如“参数是否可控”“是否存在白名单”；
  • 给出修复建议草稿；
  • 把多个工具的 findings 合并成一段更清楚的复核说明。

Agent 不应该做什么

  • 不应该凭空说“这里一定能 RCE”；
  • 不应该在没有上下文的情况下生成攻击链；
  • 不应该替代人工做最终漏洞确认；
  • 不应该接触未脱敏的敏感业务代码、凭据或真实资产信息。

这一点很重要。AI 在安全里的价值不只是“会不会发现漏洞”，还包括能不能被安全地放进工作流里。

我希望 JavaSecAtlas 怎么接 Agent

后续更理想的输入不是单独一行代码，而是一包结构化上下文：

{
  "finding": "Potential SSRF",
  "route": "POST /api/fetch",
  "controller": "FetchController#fetch",
  "auth": "no method-level annotation found",
  "param": "url",
  "source": ["JavaSecAtlas", "Semgrep"],
  "code_context": "...trimmed related snippets..."
}

Agent 基于这包材料输出：

  • 风险解释；
  • 利用条件；
  • 可能误报点；
  • 建议人工确认的问题；
  • 修复建议草稿。

最后还是要回到人工审计

我不想把 JavaSecAtlas 写成“AI 自动挖洞神器”。这个说法短期看起来吸引人，但很虚。更实际的定位是：把确定性扫描、外部工具结果、Java 项目上下文和 Agent 复核串起来，减少审计前期整理工作的重复劳动。

这也是我现在对这个项目的判断：成熟工具负责发现候选点，JavaSecAtlas 负责把候选点整理成人能看的审计线索，Agent 负责辅助解释和报告草稿，最后还是人工确认。

如果后续要继续迭代，我会优先做 finding correlation，而不是先堆更多 AI 功能。上下文没有整理好，Agent 接得越深，越容易说胡话。
