Spring SpEL EvaluationContext Java 代码审计 表达式注入

审批后台有一类功能叫“动态条件”：运营自己写表达式，存进数据库，审批时由服务端求值。产品上这么设计很合理——不同租户的审批规则差别太大，写死不如让用户配。

这类功能做安全评审时，争论通常停在同一个问题上——“表达式是运营配的，运营不是攻击者吧？”我的看法是这个问题本身问偏了。运营账号被盗、租户管理员越权、离职账号没回收、自动化系统账号被写，都是现实里发生过的路径。更该问的是：这段表达式在执行的时候，能碰到什么？

SpEL 值得写，是因为它把这个“能碰到什么”做成了一个可以配置的东西。同一个 parseExpression，换个上下文，风险能从“读错一个字段”跳到“执行任意代码”。

先分清两件事

审计里最容易混的是“表达式可控”和“变量可控”。这两件事的修复方式完全不同。

表达式可控，指的是 parseExpression() 吃进去的字符串来自用户。这种是结构注入，用户能加运算符、调方法、引用类型，等于在表达式语言里写代码。

变量可控，指的是表达式本身是常量，只有 #status、#amount 这种占位符的值来自请求。这种情况表达式的语法结构是固定的，风险要回到那些值进入了哪个方法——更接近普通业务参数，不是表达式注入。

报过几次之后我发现，大多数所谓“SpEL 注入”在第二步就断了：表达式存在配置表里，但那张表只有 DBA 能改，应用侧根本没有写入口。这种最后只能算配置项信任边界的问题，不该按 RCE 报。

一次求值要经过谁

最小的用法三行：

ExpressionParser parser = new SpelExpressionParser();
Expression expression = parser.parseExpression(expressionText);
Object value = expression.getValue(evaluationContext, rootObject);

这里有三样东西，风险各管一段：

对象它决定什么审计要看什么
expressionText表达式语法树长什么样来自请求、数据库、消息还是常量
rootObject表达式默认在谁身上取属性、调方法是裁剪过的 DTO，还是 Service、Environment、ApplicationContext
EvaluationContext属性、方法、类型、Bean 怎么解析挂了多少 resolver，注册了什么函数

大部分文章只讨论第一行。我更愿意从第三行开始看，因为同一段表达式在两个上下文里的危害不是一个量级。

EvaluationContext 才是边界

Spring 文档把 EvaluationContext 描述成“求值时用来解析属性、方法、字段和执行类型转换的接口”，主要实现有两个：StandardEvaluationContext 和 SimpleEvaluationContext。

StandardEvaluationContext 是完整版。它能配 root object，能配各种求值策略，也默认带着完整的语言能力。它本来就不是给不可信表达式准备的。

在它背后，可能挂着这些东西：

  • 类型解析，表达式里能写 T(java.lang.Runtime) 这类引用；
  • 构造器调用，表达式里能 new 对象；
  • 方法解析，能调 root object 和上下文对象上的方法；
  • Bean 解析，配了 BeanResolver 就能从 Spring 容器里取 bean；
  • 自定义函数，用 registerFunction 注册进去的静态方法；
  • 自定义 MethodResolver、PropertyAccessor，把访问面继续放大。

这些配置单独看都有正经用途。授权表达式要调 @PreAuthorize 里的 bean，规则引擎要读业务对象的属性，模板要拼接字符串。问题出在把完整能力交给了一段用户能写的文本，那就等于把一段用户控制的逻辑放进了应用进程。

SimpleEvaluationContext 是 Spring 后来补的受限版本，4.3.15 之后才有。它明确排除了类型引用、构造器和 bean 引用，属性和方法的支持级别要你自己选。典型用法：

EvaluationContext ctx = SimpleEvaluationContext
    .forReadOnlyDataBinding()
    .build();

它也不是沙箱。forReadOnlyDataBinding() 只保证不能写属性，读还是能读；root object 上有什么，它就能读到什么。但在审计里这已经是一个很明确的降级信号——至少写代码的人想过这个问题。

审计从哪下手

新项目我通常先全量 grep 一遍关键词，把命中点按“表达式来源”分堆，而不是一个个看 payload 能不能打通。

SpelExpressionParser
ExpressionParser
parseExpression
getValue
setValue
StandardEvaluationContext
SimpleEvaluationContext
TemplateParserContext
setBeanResolver
setTypeLocator
registerFunction
addMethodResolver
addPropertyAccessor

来源分几类：HTTP 参数、Header、Cookie、JSON 字段；后台配置项、规则配置、动态表单、低代码平台的计算字段；数据库里低权限可编辑的表达式模板；消息队列和任务参数；第三方回调里带的模板变量。

后台配置这一类特别容易低估。很多系统把“管理员可配”当安全边界，可后台账号是分级的，低权限运营、租户管理员、自动化系统账号都能写配置。能写一段表达式和能填一个下拉框，权限要求差得远。

分完堆再叠上下文，高风险组合大概这么几种：

组合判断原因
用户可控表达式 + StandardEvaluationContext高语言能力完整，再确认类型、方法、bean 的解析面
用户可控模板片段 + TemplateParserContext中高拼接容易绕过开发者对边界的预期
数据库表达式 + 低权限后台可编辑中高入口不在公网，但写权限边界经常比想象中松
固定表达式 + 用户只控制变量值低到中退回普通业务参数，看值进了哪个方法
SimpleEvaluationContext + 只读绑定较低能力面明显收窄，但 root object 暴露了什么仍要确认

要说清楚的是，这张表给的是复核方向，不是最终定级。同样一行“高”，一个在内网后台、只有核心运维能进，和一个在公网租户控制台，处理优先级差很多。

规则分四层

如果要做成 SAST 规则，“发现 parseExpression 就报警”没什么用。我见过的 Java 项目里，这个 API 一抓一大把，大半是常量或者内部配置。分四层会好一些。

第一层找解析点，只标候选：

new SpelExpressionParser().parseExpression(expr)

第二层追来源。这里做个轻量 taint 就够了，不必一上来铺全程序数据流：

source: request.getParameter / @RequestParam / @RequestBody field / config table / task param
sink:   parseExpression(expressionText)

第三层看上下文能力。同时出现下面几条的，提上来：用了 StandardEvaluationContext；配了 BeanResolver；注册了函数；加了自定义 MethodResolver 或 PropertyAccessor；root object 是 ApplicationContext、Environment、Service 或者其他强对象。

第四层压噪音。表达式是常量；来自只读配置且低权限改不了；用了 SimpleEvaluationContext.forReadOnlyDataBinding()；用户只能控变量值；求值前有严格的 DSL 白名单校验。这几条命中任意一条，优先级都可以往下调。

这套思路跟 JavaSecAtlas 那边的 finding 结构是对得上的：先靠关键词和 AST 找候选，再把 source、context、root object、权限入口填进报告，而不是抛一句“可能 SpEL 注入”就完事。

修的时候先问业务要什么

SpEL 的修复绕不开一个问题：业务到底需要表达式做什么？这个问题答不清楚，最后一定退化成加黑名单。而 SpEL 的语法面不是一个关键字列表能覆盖的，黑名单只会越来越长。

如果业务只是想让用户选字段、选操作符、填值，那就设计成受限 DSL，别让用户接触表达式：

// 可以:用户选字段和操作符,服务端拼
field    in ["status", "owner", "level"]
operator in ["eq", "contains", "gt"]
value    = userInput

// 不行：用户直接提交表达式
expression = userInput

必须用表达式时，优先 SimpleEvaluationContext。这句听着像套话，但落到代码上就是一行的事，而且改动成本很低。为省事直接上 StandardEvaluationContext，后面再补也就难了。

root object 尽量用裁剪过的视图对象：

class RuleContext {
    public String status;
    public String owner;
    public int score;
}

别把 Service、ApplicationContext、Environment、HttpServletRequest、Session 这些东西塞进去。root object 越像业务视图，能炸的东西越少；越像运行时对象，越收不住。

报告怎么写

“存在 SpEL 表达式注入”这种结论，开发看了也不知道从哪改。我一般把边界条件写进去：

低权限运营可在“动态审批条件”中提交表达式字符串，服务端经 SpelExpressionParser.parseExpression() 解析后，用 StandardEvaluationContext 求值，root object 为 ApprovalService 实例，未限制类型引用与方法调用。该配置入口位于管理后台，需要运营角色权限。建议改为受限 DSL，或将上下文替换为 SimpleEvaluationContext 并把 root object 收敛为只读 DTO。

多写两句话，省掉后面三轮来回：入口在哪、谁能触发、能力边界在哪、建议怎么改。
