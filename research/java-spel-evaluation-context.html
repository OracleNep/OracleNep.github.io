SpEL 表达式执行边界：从 EvaluationContext 到白盒审计

这篇不打算堆 payload。SpEL 的风险点不只在某个字符串能不能打出效果，而在于表达式来源、EvaluationContext 能力边界、解析方式和业务上下文之间的组合关系。

Spring SpEL EvaluationContext Java 代码审计 表达式注入

0. 为什么写这个方向

Java 安全里，SpEL 表达式注入很容易被写成“某个 payload 打通了”的文章。但我觉得这个方向真正值得研究的地方，不是 payload 本身，而是框架把表达式能力暴露给业务之后，开发者到底有没有把边界收住。

SpEL 是 Spring 生态里非常常见的表达式语言。它可以访问对象属性、调用方法、做集合筛选、引用类型、调用构造器，也能作为配置、模板、权限表达式、规则引擎的一部分出现。换句话说，它本来就是一个“有能力”的表达式系统。

所以审计 SpEL 风险时，不能只问：

有没有用户输入进入 parseExpression()？

更应该问：

  • 表达式字符串是不是用户可控，还是只控制变量值？
  • 使用的是 StandardEvaluationContext 还是 SimpleEvaluationContext？
  • 是否开放了类型引用、构造器、Bean 引用、方法解析器、函数注册？
  • 表达式是否以模板方式拼接，例如 #{...} 片段被动态拼进模板？
  • 这个能力出现在 Controller、后台规则配置、任务调度，还是纯内部固定配置？

这几个问题才决定一个 finding 是高危入口、后台配置风险，还是纯误报。

1. SpEL 的执行模型

一个最小的 SpEL 使用流程大概是这样：

ExpressionParser parser = new SpelExpressionParser();
Expression expression = parser.parseExpression(expressionText);
Object value = expression.getValue(evaluationContext, rootObject);

这里至少有三个角色：

角色作用审计关注点
expressionText被解析的表达式字符串是否来自请求、数据库、消息队列、低权限配置
rootObject表达式默认操作的业务对象是否包含敏感对象、服务类、环境配置、上下文对象
EvaluationContext决定属性、方法、类型、Bean、转换器等解析方式是否给了过宽的反射和解析能力

很多文章会把注意力都放在 expressionText 上，但我更关心 EvaluationContext。因为同一段表达式，在不同上下文里完全不是一个风险等级。

例如，一个只允许读属性的上下文，和一个可以访问类型、调用方法、解析 Bean 的上下文，安全边界不是一个量级。前者更像受限数据绑定，后者更接近一个可扩展的表达式执行环境。

2. EvaluationContext 是安全边界

Spring 官方文档里把 EvaluationContext 描述为表达式求值时解析属性、方法、字段以及类型转换的 API，并提供了两个主要实现：SimpleEvaluationContext 和 StandardEvaluationContext。

StandardEvaluationContext 暴露完整的 SpEL 语言特性和配置选项，可以配置 root object，也可以配置各种求值策略。它适合可信表达式场景，但如果表达式字符串可控，就要非常小心。

SimpleEvaluationContext 的设计目标是只暴露 SpEL 的必要子集，适合那些不需要完整 SpEL 语法、并且应该被限制的表达式类别。官方文档也明确提到，它会排除 Java 类型引用、构造器和 Bean 引用，并要求开发者显式选择属性和方法支持级别。

2.1 为什么 StandardEvaluationContext 容易变成危险放大器

在安全审计里，我会把 StandardEvaluationContext 当成能力放大器，而不是单纯的普通参数。

原因是它背后可能挂了这些东西：

  • 类型解析能力，例如表达式中引用 Java 类型；
  • 构造器解析能力，例如创建新对象；
  • 方法解析能力，例如调用 root object 或上下文对象上的方法；
  • Bean 解析能力，例如访问 Spring 容器里的 Bean；
  • 自定义函数，例如把某些 Java 方法注册为表达式函数；
  • 属性访问器和类型转换器，例如扩大对象访问面。

这些能力本身不是漏洞，但如果表达式文本被低权限用户控制，风险就从“解析字符串”变成了“把一段用户控制的逻辑放到应用上下文里执行”。

2.2 SimpleEvaluationContext 的价值

SimpleEvaluationContext 的价值在于，它逼你先回答一个问题：业务到底需要表达式做什么？

如果只是做数据绑定、属性读取、简单过滤，那就没有必要把完整 SpEL 能力打开。很多项目的问题不是“用了 SpEL”，而是“明明只需要读属性，却给了完整执行上下文”。

EvaluationContext ctx = SimpleEvaluationContext
    .forReadOnlyDataBinding()
    .build();

这类上下文并不是万能安全沙箱，但至少能把类型引用、构造器、Bean 引用这些高风险能力从默认面上拿掉。对审计来说，这就是一个非常重要的降级信号。

3. 白盒审计的 sources 与 sinks

做 SpEL 审计，我通常不会从 payload 出发，而是从数据流出发。

3.1 重点 sources

表达式字符串可能来自这些地方：

  • HTTP 参数、Header、Cookie、JSON 字段；
  • 后台配置项、规则配置、动态表单、低代码平台字段；
  • 数据库中可由低权限用户编辑的表达式模板；
  • 消息队列、任务调度参数、Webhook 配置；
  • 第三方集成回调中的模板变量或条件表达式。

这里有一个容易被忽略的点：不一定只有公网请求参数才算 source。很多后台系统会把“管理员可配”当成安全边界，但现实里后台账号经常分级，低权限运营、租户管理员、自动化系统账号都可能写配置。能写表达式和能写普通配置，不是一个权限级别。

3.2 重点 sinks

代码里可以优先搜这些关键词：

SpelExpressionParser
ExpressionParser
parseExpression
getValue
setValue
StandardEvaluationContext
SimpleEvaluationContext
TemplateParserContext
setBeanResolver
setTypeLocator
registerFunction
addMethodResolver
addPropertyAccessor

其中 parseExpression() 只是入口，真正决定风险等级的往往是后续的 getValue()、上下文类型、root object，以及有没有额外配置 BeanResolver / MethodResolver / PropertyAccessor。

3.3 高风险组合

组合风险判断原因
用户可控表达式 + StandardEvaluationContext高表达式能力完整，后续需要确认类型、方法、Bean 等解析面
用户可控模板片段 + TemplateParserContext中高容易在字符串拼接中绕过开发者预期
数据库表达式 + 后台低权限可编辑中高攻击面不在公网入口，但权限边界容易被低估
固定表达式 + 用户只控制变量值低到中更像普通业务参数，重点看变量进入的业务方法
SimpleEvaluationContext + 只读属性绑定较低能力面被明显收窄，但仍需确认 root object 是否暴露敏感属性

4. 规则设计与误报压缩

如果把这个方向写成 SAST 规则，我不会只写一条“发现 parseExpression 就报警”。这样误报太多，也体现不出研究价值。

更合理的是分层规则：

4.1 第一层：表达式解析点

new SpelExpressionParser().parseExpression(expr)

这一层只标记为候选点，不直接定性。因为 expr 可能是常量，也可能来自可信配置。

4.2 第二层：表达式来源

继续追 expr 是否来自请求参数、JSON、数据库字段、后台配置、消息参数。这里可以做轻量 taint，不需要一上来就做全程序数据流。

source: request.getParameter / @RequestParam / @RequestBody field / config table / task param
sink:   parseExpression(expressionText)

4.3 第三层：上下文能力

如果同时出现下面这些点，风险等级应该上调：

  • 使用 StandardEvaluationContext；
  • 设置了 BeanResolver；
  • 注册了函数；
  • 加入了自定义 MethodResolver / PropertyAccessor；
  • root object 是 ApplicationContext、Environment、Service、工具类集合等强对象。

4.4 第四层：降噪条件

这些情况可以降低优先级：

  • 表达式是字符串常量；
  • 表达式来自只读内部配置且不可被低权限修改；
  • 使用 SimpleEvaluationContext.forReadOnlyDataBinding()；
  • 只允许用户控制变量值，不允许控制表达式结构；
  • 表达式执行前有严格白名单 DSL 校验。

这个规则思路也能和 JavaSecAtlas 后续结合：先通过关键词和 AST 找候选点，再把 source、context、root object、权限入口整理进报告，而不是单纯抛一个“可能 SpEL 注入”。

5. 修复与加固建议

修 SpEL 风险，不应该只靠黑名单。黑名单很容易漏，因为 SpEL 的语法面不是单一关键字能概括的。更稳的思路是先收缩能力，再限制输入。

5.1 最优先：不要让用户控制表达式结构

如果业务只是想让用户选择字段、条件、排序、过滤逻辑，尽量设计成受限 DSL 或枚举配置，而不是直接让用户写 SpEL。

// 推荐方向：用户选择受限字段和操作符
field in ["status", "owner", "level"]
operator in ["eq", "contains", "gt"]
value = userInput

// 不推荐：用户直接提交完整表达式
expression = userInput

5.2 必须用表达式时，优先使用 SimpleEvaluationContext

如果业务只需要属性读取或简单数据绑定，优先考虑：

EvaluationContext ctx = SimpleEvaluationContext
    .forReadOnlyDataBinding()
    .build();

不要为了省事直接上 StandardEvaluationContext。这不是代码风格问题，而是能力边界问题。

5.3 不要把强对象作为 root object 暴露出去

表达式上下文里的 root object 应该是裁剪后的 DTO，而不是 Service、ApplicationContext、Environment、Request、Session 或一堆工具类集合。

class SafeRuleContext {
    public String status;
    public String owner;
    public int score;
}

root object 越像业务视图模型，风险越可控；越像应用运行时对象，风险越难收。

5.4 审计报告里怎么写结论

我一般不会直接写“存在 SpEL RCE”。更稳的报告表述应该包含边界条件：

发现业务允许低权限用户提交表达式字符串，并通过 SpelExpressionParser.parseExpression() 使用 StandardEvaluationContext 进行求值。该上下文暴露完整 SpEL 能力，且表达式执行对象包含业务服务对象。建议改为受限 DSL 或 SimpleEvaluationContext，并禁止用户控制表达式结构。

这样比直接扔 payload 更像真实审计报告，也更容易让开发理解问题在哪。

6. 总结

SpEL 表达式注入的关键，不是背几个 payload，而是理解表达式引擎的能力边界。

我会把审计重点放在四件事上：

  1. 表达式字符串是否可控；
  2. 使用了什么 EvaluationContext；
  3. 上下文里暴露了哪些解析能力和对象；
  4. 这个能力处在哪个业务权限边界里。

如果这四个问题能回答清楚，一个 SpEL finding 的风险等级基本也就能判断清楚了。后续如果把这套思路做进 JavaSecAtlas，可以比“命中 parseExpression 就报警”的规则更接近真实代码审计。
