Java JNDI JNDI 注入 InitialContext.lookup Java 代码审计 JVM 安全

0. 研究问题与边界

JNDI 注入最容易被讲成“某个字符串触发远程加载”的故事，但对真实 Java 代码审计来说，这个描述既不够精确，也不利于修复。更稳的研究问题应该是：当一段不可信数据进入 JNDI lookup 时，JVM、JNDI provider、URL Context、对象工厂和业务代码共同暴露了哪些执行能力？

本文聚焦 Java 安全中的一个细分领域：JNDI lookup 边界与白盒审计。我不会堆叠利用载荷，而是从 JNDI 机制本身拆解风险，把一个 finding 拆成可审计、可定级、可修复的工程问题。

核心结论：JNDI 注入不是一个单点漏洞，而是一类“把用户可控名称交给命名服务解析”的能力泄露。风险等级取决于名称是否可控、协议是否可控、JDK 与依赖版本、对象工厂是否可达、网络出口是否开放、返回对象如何被业务使用。

因此，一个成熟的 Java JNDI 注入审计报告不应该只写“参数进入 lookup()，可能 RCE”。更好的报告需要说明：

  • 用户是否能控制完整 JNDI 名称，还是只能控制受限片段；
  • 名称是否可能被解析为 ldap:、rmi:、iiop: 等 URL Context；
  • 运行时是否允许远程 codebase，或者 classpath 内是否存在可被对象工厂利用的本地类；
  • 应用是否有对外 LDAP/RMI/DNS 访问能力，是否会造成 SSRF、信息泄露或资产探测；
  • 返回对象是否继续被强转、反射调用、反序列化、表达式求值或写入 Spring 容器。

1. JNDI 的执行模型

JNDI，全称 Java Naming and Directory Interface，本质上是 Java 为命名服务和目录服务提供的一层统一 API。对开发者来说，它常见于数据源、JMS、LDAP、EJB、RMI、应用服务器资源查找等场景。危险点在于：lookup(String name) 接收的是“名称”，但这个名称不一定只是普通 key，它可能触发 provider 选择、URL Context 构造、远程目录访问和对象工厂实例化。

1.1 最小调用路径

Context ctx = new InitialContext();
Object object = ctx.lookup(name);

在白盒审计里，这两行代码可以拆成三个问题：

阶段安全问题审计关注点
名称构造name 是否可控HTTP 参数、Header、JSON、数据库配置、消息队列、任务配置是否进入 lookup
上下文选择是否触发 URL Context名称是否以可解析 scheme 开头，是否绕过业务前缀拼接和黑名单
对象解析返回对象如何生成是否涉及 Reference、ObjectFactory、本地 classpath 工厂或远程目录返回对象

1.2 InitialContext.lookup 不是普通 Map 查询

从 API 语义看，InitialContext.lookup(String) 是“检索命名对象”。这和 Map.get(key) 的直觉不同：JNDI 名称会进入 provider 解析流程，且某些名称形式会被当作 URL 处理。Oracle 的 InitialContext 文档明确把 lookup(String name) 定义为检索指定名称绑定的对象，这意味着调用者拿到的是 provider 解析后的对象，而不是静态字符串映射。

简化成伪代码，大致可以这样理解：

Object lookup(String name) {
    Context context = resolveInitialOrURLContext(name);
    Object raw = context.lookup(name);
    return maybeDecodeReference(raw, environment);
}

这里的 resolveInitialOrURLContext 和 maybeDecodeReference 才是安全边界。审计时如果只看 lookup 这一行，很容易把真实风险低估或高估。

1.3 NamingManager.getObjectInstance 是对象化边界

NamingManager.getObjectInstance() 是 JNDI 中非常关键的对象工厂入口。根据 Java API 文档，它会根据 Reference / Referenceable、URL 地址、Context.OBJECT_FACTORIES 等策略尝试创建对象。换句话说，JNDI 不只是“查名字”，还可能把目录服务返回的引用信息转成 Java 对象。

// 伪代码：表达审计模型，不是 JDK 源码逐字复制
Object getObjectInstance(Object refInfo, Name name, Context ctx, Hashtable env) {
    if (refInfo contains factoryClassName) {
        ObjectFactory factory = loadFactory(factoryClassName, env);
        return factory.getObjectInstance(refInfo, name, ctx, env);
    }
    if (refInfo contains URL address) {
        Context urlCtx = getURLContext(scheme, env);
        return urlCtx.lookup(url);
    }
    for (factoryName : env.get(Context.OBJECT_FACTORIES)) {
        try factoryName as ObjectFactory;
    }
    return refInfo;
}

这段模型带来的审计启发是：即使现代 JDK 默认收紧了远程 class loading，JNDI 仍然可能通过本地 classpath 中已有的 ObjectFactory、应用服务器内置工厂、JMS/LDAP 客户端行为、URL Context 访问等路径产生风险。升级 JDK 是必要条件，但不是完整修复。

2. 从远程 class 到本地工厂：JNDI 风险的历史演进

早期 JNDI 风险经常和“远程 codebase 加载类”绑定在一起。JDK 后续逐步收紧了相关默认行为，例如 Oracle JDK 8u121 的 release notes 明确提到，RMI Registry 与 COS Naming service provider 通过 JNDI object factory 进行远程 class loading 默认被禁用，需要显式设置 com.sun.jndi.rmi.object.trustURLCodebase 或 com.sun.jndi.cosnaming.object.trustURLCodebase 才能启用。

但从审计角度看，JNDI 风险并没有因为默认远程加载收紧而消失，而是从“远程拉 class”转向了更依赖运行时上下文的组合风险：

阶段典型风险审计重点
远程 codebase 阶段目录服务返回远程类位置，客户端加载并实例化JDK 版本、trustURLCodebase、SecurityManager 历史配置
本地工厂阶段返回对象触发 classpath 中已有 ObjectFactory 或容器工厂依赖树、应用服务器、Spring/Tomcat/BeanFactory 等可达类
出口与探测阶段lookup 导致 LDAP/RMI/DNS 等外连SSRF、内网探测、DNS log、认证信息泄露、超时 DoS
业务对象阶段返回对象被强转、反射调用或进入配置流程返回对象后续使用链、类型校验、异常处理和日志泄露

所以，“JDK 已升级”只能作为降低风险的证据之一。真正的修复是阻断低权限用户控制 JNDI 名称结构，并把动态 lookup 限定在可信命名空间里。

3. Log4Shell 给 JNDI 审计带来的启发

Log4Shell 并不只是 Log4j 的一个历史事件，它把 JNDI 风险从“框架内部能力”暴露成了供应链层面的系统性问题。Apache Logging Services 的安全页面对 CVE-2021-44228 的描述非常直接：Log4j 中用于配置、日志消息和参数的 JNDI 特性没有防护攻击者控制的 LDAP 和其他 JNDI 相关端点，攻击者控制日志消息或参数时可能执行从 LDAP 服务加载的代码。该漏洞影响 log4j-core 的特定版本区间，CVSS 3.x 评分为 10.0。

这件事对 Java 代码审计有三个启发：

  1. 不可信输入不一定来自 Controller。 日志消息、MDC、线程上下文、配置插值、异常消息、第三方回调都可能成为 source。
  2. 危险 sink 不一定在业务代码里显式出现。 业务只是在记录日志，但框架内部可能执行 lookup、插值、解析器和插件逻辑。
  3. 修复不应该只靠过滤 payload。 Log4j 后续的修复方向是禁用/限制危险 lookup 能力、调整默认行为和升级版本，而不是要求所有业务代码做字符串黑名单。
从方法论上看，Log4Shell 之后的 JNDI 审计应该从“找字符串模式”升级为“找解析能力暴露点”：谁把不可信数据交给了一个能访问命名服务、能对象化返回值、能触发网络出口的组件？

4. 代码级风险拆解：一个可复核的最小模型

下面的代码不是攻击示例，而是审计中常见的“危险模式最小化”。它模拟后台系统允许租户配置资源名称，服务端根据这个名称做 JNDI lookup。

public final class TenantResourceResolver {
    public Object resolve(String tenantId, String configuredName) throws NamingException {
        // configuredName 来自数据库，低权限租户管理员可修改
        Context ctx = new InitialContext();
        return ctx.lookup(configuredName);
    }
}

这段代码的漏洞点不在于 InitialContext 本身，而在于 configuredName 的权限边界被误判了。很多系统把“后台可配置”当成可信输入，但多租户后台、运营后台、插件配置、Webhook 配置都可能被低权限用户控制。

4.1 风险不是二元判断，而是能力矩阵

审计问题低风险答案高风险答案
用户能控制什么只能选择枚举 ID能写完整 JNDI 名称或 URL
命名空间固定 java:comp/env/ 前缀并 canonicalize允许任意 scheme 或拼接后可绕过
网络出口容器层禁止访问外部 LDAP/RMI/DNS应用可访问互联网或敏感内网
返回对象只允许固定接口类型，失败即拒绝返回对象进入反射、表达式、Bean 注册或脚本执行
依赖环境依赖裁剪，无危险 ObjectFactoryclasspath 有可被 Reference 触达的工厂类

4.2 常见的伪修复

// 不推荐：看似限制了 ldap，但没有建立可信命名空间
if (configuredName.toLowerCase(Locale.ROOT).contains("ldap")) {
    throw new IllegalArgumentException("blocked");
}
return new InitialContext().lookup(configuredName);

黑名单的问题是：它只是在和输入形态对抗，而不是在限制能力。JNDI provider、URL scheme、大小写、编码、前缀拼接、容器内置命名空间和后续对象处理都会让黑名单变得脆弱。

4.3 更稳的修复模型

public final class SafeJndiResolver {
    private static final String SAFE_PREFIX = "java:comp/env/app/resources/";
    private static final Pattern SAFE_NAME = Pattern.compile("[a-zA-Z0-9_.-]{1,64}");

    public DataSource resolveDataSource(String logicalName) throws NamingException {
        if (!SAFE_NAME.matcher(logicalName).matches()) {
            throw new IllegalArgumentException("invalid resource name");
        }

        String jndiName = SAFE_PREFIX + logicalName;
        Object value = new InitialContext().lookup(jndiName);

        if (!(value instanceof DataSource ds)) {
            throw new NamingException("unexpected JNDI object type: " + value.getClass().getName());
        }
        return ds;
    }
}

这段修复代码的核心不是正则，而是能力收缩：

  • 用户只能控制逻辑名，不能控制完整 JNDI URL；
  • 服务端强制固定命名空间；
  • 返回对象必须是预期类型；
  • 失败时拒绝，而不是 fallback 到另一个 lookup；
  • 资源命名和权限边界一致，租户只能访问自己的资源配置。

4.4 对 Spring 代码的同类审计

Spring 项目里不一定直接出现 new InitialContext()，还可能包在 JndiTemplate、JndiObjectFactoryBean 或框架配置里。

// 候选风险：name 来自配置中心或数据库，且低权限用户可改
JndiTemplate template = new JndiTemplate();
Object value = template.lookup(name);

这类 finding 的审计重点是配置来源。只要 name 是固定部署配置，并且配置文件只能由可信运维修改，风险通常低很多；如果配置来自租户后台、动态规则表、插件市场或灰度平台，就要按不可信输入继续追。

5. 白盒审计的 sources 与 sinks

做 JNDI 注入审计时，我会先建立 source / sink / context 三层模型，而不是直接报高危。

5.1 高价值 sources

  • HTTP 参数、Header、Cookie、JSON 字段、GraphQL 参数；
  • 数据库中的租户配置、规则配置、连接器配置、Webhook 配置；
  • 配置中心、Nacos、Apollo、Consul、Spring Cloud Config 中可由非核心运维修改的 key；
  • 消息队列、任务调度参数、CI/CD 变量、插件 manifest；
  • 日志消息、MDC / ThreadContext、异常 message、模板变量；
  • 上传文件中的 XML/YAML/Properties 配置片段。

5.2 重点 sinks

InitialContext.lookup
Context.lookup
Context.lookupLink
InitialDirContext.search
NamingManager.getObjectInstance
DirectoryManager.getObjectInstance
JndiTemplate.lookup
JndiObjectFactoryBean.setJndiName
JmsAppender / JMSAppender configuration
DataSourceLookup / JndiDataSourceLookup

其中 search 类 API 不一定等价于对象工厂实例化，但仍然可能造成 LDAP 注入、信息泄露、认证绕过或目录探测。审计时要区分“JNDI 名称注入”和“LDAP filter 注入”，不要混成一个结论。

5.3 影响定级的上下文

上下文证据风险影响
JDK 版本较新且默认禁用远程 codebase降低远程加载类的可能性，但不排除本地工厂、SSRF 和信息泄露
容器网络禁止外连 LDAP/RMI/DNS明显降低远程交互风险，但仍要看本地命名空间是否越权
lookup 名称固定为 java:comp/env/...通常降级，但要确认用户不能逃逸前缀或控制完整名称
返回对象被用于反射、脚本、表达式或 Bean 注册上调风险，因为对象化结果进入更强执行上下文
异常信息完整回显给用户可能形成探测 oracle，帮助枚举 provider、内部地址和依赖版本

6. 规则设计与误报压缩

如果把 JNDI 注入做成 SAST 规则，最差的写法是“发现 lookup 就报警”。企业代码里合法 JNDI lookup 很多，这样会制造大量噪音。更合理的是分层打分。

6.1 Semgrep 风格的候选规则

rules:
  - id: java-jndi-lookup-candidate
    languages: [java]
    message: "JNDI lookup candidate: confirm whether the name is user-controlled and whether URL Context is allowed."
    severity: WARNING
    patterns:
      - pattern-either:
          - pattern: new InitialContext().lookup($NAME)
          - pattern: $CTX.lookup($NAME)
          - pattern: $TEMPLATE.lookup($NAME)
      - metavariable-pattern:
          metavariable: $NAME
          pattern-not: "java:comp/env/..."

这条规则只适合找候选点，不应该直接输出高危。下一步要结合 taint source 和上下文证据。

6.2 JavaSecAtlas 可以怎么组织 finding

Finding {
  rule_id: "java.jndi.lookup.user-controlled-name",
  sink: "InitialContext.lookup(configuredName)",
  source: "tenant_config.resourceName",
  route: "POST /api/tenant/resource/update",
  permission: "TENANT_ADMIN",
  jndi_namespace: "unrestricted",
  outbound_network: "unknown",
  object_factory_surface: "classpath-dependent",
  severity: "high if full name is controllable; medium if only internal namespace"
}

这种结构比“可能 JNDI 注入”更有复核价值：它把入口、权限、sink、命名空间、网络出口和依赖上下文放在一起，方便人工判断。

6.3 降噪规则

  • lookup("java:comp/env/jdbc/app") 这类字符串常量默认低优先级；
  • 名称来自只读部署配置，且配置仓库只有核心维护者可写，可以降级；
  • 用户只控制逻辑 ID，服务端拼接固定安全前缀并校验类型，可以降级；
  • 出现 ldap://、rmi://、iiop:// 等协议常量不等于漏洞，但应该检查是否和不可信输入拼接；
  • 出现 Context.OBJECT_FACTORIES、自定义 ObjectFactory、自定义 InitialContextFactory 时，上调复核优先级。

7. 修复与工程化防护

JNDI 注入的防御不要停留在字符串过滤。更稳的顺序是：先收缩能力，再限制输入，最后用运行时策略兜底。

7.1 设计层：不要让用户控制 JNDI 名称结构

如果业务只是想让用户选择数据源、消息队列或目录资源，应该暴露逻辑 ID，而不是暴露 JNDI 名称。

// 推荐：用户提交 resourceId，服务端映射到固定 JNDI 名称
Map<String, String> resourceMap = Map.of(
    "main", "java:comp/env/app/resources/mainDataSource",
    "audit", "java:comp/env/app/resources/auditDataSource"
);
String jndiName = resourceMap.get(userSelectedId);

7.2 代码层：allowlist + canonicalization + 类型校验

  • 只允许固定 scheme 或固定容器命名空间；
  • 对逻辑名做长度、字符集和路径片段校验；
  • 禁止 fallback 到用户原始输入；
  • lookup 后进行严格类型校验；
  • 异常日志保留内部细节，但对外只返回通用错误。

7.3 运行时层：网络出口与依赖面控制

  • 默认禁止应用容器访问外部 LDAP、RMI、DNS 解析器以外的任意 DNS、IIOP 等服务；
  • 用 egress policy、Kubernetes NetworkPolicy、Service Mesh 或云安全组限制出站；
  • 做依赖治理，避免无关 JNDI provider、JMS appender、旧版 Log4j 或危险 ObjectFactory 出现在 classpath；
  • 对日志、配置中心和租户后台的输入建立统一的“不可信数据”模型；
  • 在 RASP / Agent / eBPF 侧监控异常 JNDI、LDAP、RMI 出站行为。

7.4 报告模板

发现低权限租户管理员可修改资源配置字段 resourceName，该字段进入 InitialContext.lookup() 并作为完整 JNDI 名称解析。当前代码未限制命名空间、协议或返回对象类型。该问题可能导致非预期 JNDI provider 访问、内部网络探测、目录信息泄露，并在特定 JDK / classpath / 对象工厂组合下扩大为代码执行风险。建议改为服务端维护资源 ID 到固定 java:comp/env/... 名称的映射，并增加协议 allowlist、类型校验和网络出口限制。

7.5 总结

JNDI 注入的核心不是某个历史 payload，而是 Java 应用把“命名解析能力”交给了不可信输入。审计时要把 lookup() 当成一个能力边界：它可能访问网络、选择 provider、对象化返回值、触发本地工厂，并把结果继续交给业务代码。

真正有价值的 Java 安全研究，应该能帮助后来的人把 finding 复核清楚：哪里是 source，哪里是 sink，哪里是上下文放大器，哪里是可以落地的修复边界。JNDI 这个方向尤其如此，因为它横跨 JVM、JDK、框架、容器、依赖树和企业网络出口，任何单点解释都容易失真。
