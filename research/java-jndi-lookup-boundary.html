JNDI 注入的执行边界：从 InitialContext.lookup 到 NamingManager 的白盒审计

很多人把 JNDI 当成“能不能拉一个 class 下来”来判断。实际审计里，更常见的问题是这个应用把“解析一个名字”的能力交给了谁，以及名字后面跟着的那一串东西。

Java JNDI JNDI 注入 InitialContext.lookup Java 代码审计 JVM 安全

多租户后台里有一类代码很常见：资源名存在租户配置表里，服务端读出来直接交给 InitialContext.lookup()。写这段代码的人多半认为它是后台配置，属于可信输入。能改那张表的，往往就是租户管理员。

顺着往下看，能问的东西比想象中多。这个字段能不能写成带 scheme 的完整名称？容器里有没有现成可用的 ObjectFactory？那台机器出不出得去？三个问题的答案不同，定的级别就不同。只看 lookup 那一行，什么也定不下来。

这篇想把这个过程拆开：名字从进来，到被解析成对象，中间经过哪几步，每步各自暴露了什么能力，审计的时候在哪里停下来。利用链和 payload 不是重点。

lookup 不只是查一个 key

JNDI 是 Java 给命名服务和目录服务套的一层统一 API。数据源、JMS、LDAP、EJB、应用服务器资源，最后往往都落到同一种写法：

Context ctx = new InitialContext();
Object obj = ctx.lookup(name);

按 Map.get() 的直觉理解，这就是查表。实际不是。名字要先被解释：决定用哪个 provider，判断它是不是一个 URL，然后把结果交回来。交回来的可能是字符串，可能是远程对象的代理，也可能是目录服务返回的一个 Reference。

写成伪代码大概是： 

Object lookup(String name) {
    Context ctx = getURLOrDefaultInitCtx(name);  // 带 scheme 就走 URL Context
    Object raw = ctx.lookup(name);
    return resolve(raw);                         // Reference 可能被对象化
}

有注释的两行才是要停下来的地方。getURLOrDefaultInitCtx 决定这次查找会不会跑到别的服务上，resolve 决定拿回来的是数据还是对象。审计只看 lookup 那一行，等于把这两件事都跳过去了。

Oracle 文档对 lookup(String) 的说明只有“检索指定名称绑定的对象”这一句，不解释名字会被怎么理解。这也是为什么同一个 API，在报告里既能写成信息泄露，也能写成 RCE，全看上下文给到哪一步。

对象化发生在 NamingManager

名字解析完，如果拿到的是 Reference，JNDI 会去找工厂把它变成对象。入口是 NamingManager.getObjectInstance()，可用的工厂有三个来源：Reference 自己带的类名、里面的 URL 地址，以及环境属性 Context.OBJECT_FACTORIES 里注册的类。

// 表达调用顺序，不是 JDK 源码逐行复制
Object getObjectInstance(Object refInfo, Name name, Context ctx, Hashtable env) {
    if (refInfo contains factoryClassName) {
        ObjectFactory f = loadFactory(factoryClassName, env);
        return f.getObjectInstance(refInfo, name, ctx, env);
    }
    if (refInfo contains URL address) {
        return getURLContext(scheme, env).lookup(url);
    }
    for (String f : env.get(Context.OBJECT_FACTORIES)) { /* 逐个尝试 */ }
    return refInfo;
}

所以 JNDI 的危险不只来自“从远处拉一个 class”。目录服务返回的是一段描述，描述里可以点名要哪个工厂。那个工厂是否已经在本地 classpath 上，直接决定了一半的结论。

远程加载收紧了，本地工厂还在

最早的利用方式依赖远程 codebase：RMI Registry 或 COS Naming 返回一个带 javaCodebase 的引用，客户端照着地址去下载并实例化。8u121 之后这条路默认关掉了，要显式打开 com.sun.jndi.rmi.object.trustURLCodebase 或 com.sun.jndi.cosnaming.object.trustURLCodebase；LDAP provider 那一侧对应的是 8u191 前后的 com.sun.jndi.ldap.object.trustURLCodebase。

“默认关掉”经常被读成“这条线结束了”。我一般会补一句：变难的是远程拉 class 这一步，JNDI 交出去的能力没有只剩这一步。

阶段典型风险审计要看什么
远程 codebase目录返回类的位置，客户端下载并实例化JDK 版本、trustURLCodebase 设置、历史上是否开过 SecurityManager
本地工厂返回对象触发 classpath 里已有的 ObjectFactory 或容器工厂依赖树、应用服务器、Spring / Tomcat 暴露的可用类
出口与探测lookup 带出 LDAP / RMI / DNS 连接SSRF、内网可达性、认证信息泄露、超时挂起
业务对象返回对象被强转、反射调用、注册进容器类型校验、后续调用链、异常信息是否回显

四行里只有第一行跟 JDK 版本强相关。另外三行升级 JDK 也带不走，所以“已经升到 8u3xx”是一条减轻证据，不是修复结论。

Log4Shell 留下的三个提醒

CVE-2021-44228 值得单独说，不是因为它有名，而是它把 JNDI 从组件内部的实现细节推到了所有人面前。Log4j 处理日志消息时解析 ${jndi:...}，攻击者控制消息内容就够了，不需要碰业务代码。受影响的是 log4j-core 2.0-beta9 到 2.14.1，CVSS 10.0。

这件事我有三条记下来，后来写报告经常用得上。

一是 source 会跑出 Controller。日志消息、MDC、异常 message、配置插值、第三方回调，都能把不可信数据往下游送。按“入口只有 HTTP 参数”去找，很容易漏。

二是 sink 可能不在业务代码里。业务只是在打日志，真正执行 lookup 的是框架。这类点在静态扫描里往往表现为“命中处看不出危险”，得顺着依赖往里走一层。

三是修复方向。Log4j 后面几个版本做的是关掉危险 lookup、改默认行为、限制允许的协议，没有让所有业务方去过滤字符串。这个思路对自研系统同样成立。

一段看起来没问题的代码

回到开头那段，补全一点：

public final class TenantResourceResolver {
    public Object resolve(String tenantId, String configuredName) throws NamingException {
        // configuredName 来自租户配置表，租户管理员可改
        Context ctx = new InitialContext();
        return ctx.lookup(configuredName);
    }
}

问题不在 InitialContext，在“后台可配置”被当成了“可信”。多租户后台、运营后台、插件配置、Webhook 配置，写入权限往往比开发者以为的宽。能改配置和能写代码不是一回事，能填一个资源 ID 和能写一个完整的 JNDI 名字也不是一回事。

所以定级时我不用“是漏洞/不是漏洞”来分，而是看下面几道题各自答成什么样：

问题低风险高风险
用户能控制什么只能选枚举 ID能写完整名称或 URL
命名空间固定前缀，拼完再校验任意 scheme，或者拼接后能被绕开
网络出口容器层禁止访问外部 LDAP / RMI / DNS能访问互联网或内网敏感段
返回对象只接受固定接口类型，不匹配就拒绝进反射、表达式求值、Bean 注册
依赖环境classpath 干净，没有能用的工厂类有能被 Reference 触发的 ObjectFactory

五行的答案凑齐，报告才写得下去。如果只有第一行是“是”，后面几行都空着，那这条最多算一个待确认项，不该直接标高危。

黑名单为什么不够

这类问题的第一个修复尝试通常是过滤。见过最多的写法：

if (name.toLowerCase(Locale.ROOT).contains("ldap")) {
    throw new IllegalArgumentException("blocked");
}
return new InitialContext().lookup(name);

这段漏了 rmi:，是明面上的。更要紧的是它在和字符串形态对抗，不是在限制能力。scheme 大小写、前后空白、拼接顺序、容器自己的命名空间，换一处就要补一条规则，补到最后规则本身成了需要审计的对象。

另外，search() 那条线不是同一种问题。InitialDirContext.search 拿到可控 filter 时是 LDAP filter 注入，结论一般是越权读取或信息泄露，跟 lookup 的对象化没多大关系。报告里混着写，复核的人会看不明白。

收窄能力，而不是过滤字符串

能用的修复长得都差不多：让用户能控制的东西变少，而不是让检查变多。

public final class SafeJndiResolver {
    private static final String PREFIX = "java:comp/env/app/resources/";
    private static final Pattern NAME = Pattern.compile("[a-zA-Z0-9_.-]{1,64}");

    public DataSource resolveDataSource(String logicalName) throws NamingException {
        if (!NAME.matcher(logicalName).matches()) {
            throw new IllegalArgumentException("invalid resource name");
        }
        Object value = new InitialContext().lookup(PREFIX + logicalName);
        if (!(value instanceof DataSource ds)) {
            throw new NamingException("unexpected type: " + value.getClass().getName());
        }
        return ds;
    }
}

正则不是重点。重点有四条：用户只能填逻辑名，填不了完整 URL；前缀由服务端固定；拿回来的东西必须是指定类型；类型不对就报错，不 fallback 到另一次 lookup。

更彻底的做法是不让用户碰名字：

Map<String, String> resources = Map.of(
    "main",  "java:comp/env/app/resources/mainDataSource",
    "audit", "java:comp/env/app/resources/auditDataSource"
);
String jndiName = resources.get(userSelectedId);

用户提交 main 或 audit，映射在代码里。这样 JNDI 名字根本不是输入，前面那些过滤规则也不需要了。剩下的风险只在于表里那几条映射写得对不对。

Spring 项目里不一定能直接看到 new InitialContext()，中间可能包着 JndiTemplate 或 JndiObjectFactoryBean：

JndiTemplate template = new JndiTemplate();
Object value = template.lookup(name);

这种情况审计重点从 API 挪到了配置来源。name 是部署时写死的、配置文件只有运维能改，风险低很多；如果来自租户后台、动态规则表、插件市场，那就照不可信输入继续追。

审计时先找什么

我一般不从 payload 出发，从数据流出发。顺序是 source、sink、上下文证据，最后才定级。

source 除了 HTTP 参数、Header、Cookie、JSON 字段这些常规位置，还有几类容易被放过：数据库里的租户配置和连接器配置；配置中心里非核心运维能改的 key；任务调度参数、CI 变量、插件 manifest；日志消息和 MDC；上传文件里的 XML / YAML / properties 片段。

sink 可以先按关键词扫一遍：

InitialContext.lookup
Context.lookup
Context.lookupLink
InitialDirContext.search
NamingManager.getObjectInstance
DirectoryManager.getObjectInstance
JndiTemplate.lookup
JndiObjectFactoryBean.setJndiName
JMSAppender
JndiDataSourceLookup

扫出来的都是候选。真正拉开级别的是上下文：JDK 版本、出网策略、命名空间是否固定、返回对象后面谁在用、异常会不会回显给用户。最后一项经常被忽略——一个能稳定区分“名字存在/不存在”的报错，本身就是探测用的 oracle。

规则先找候选，再定级

做成 SAST 规则，最差的一版是“看到 lookup 就报高危”。企业代码里合法的 lookup 太多，这么写只会被关掉。

Semgrep 我会先写一条纯候选规则：

rules:
  - id: java-jndi-lookup-candidate
    languages: [java]
    message: "JNDI lookup candidate: confirm name controllability and URL context."
    severity: WARNING
    patterns:
      - pattern-either:
          - pattern: new InitialContext().lookup($NAME)
          - pattern: $CTX.lookup($NAME)
          - pattern: $TPL.lookup($NAME)

输出 WARNING 而不是 ERROR，是因为这条规则回答不了“名字可不可控”。下一步要么接 taint，要么人工看上下文。

finding 的结构我倾向于把上下文摊开，而不是给一句“可能 JNDI 注入”：

rule_id:   java.jndi.lookup.user-controlled-name
sink:      InitialContext.lookup(configuredName)
source:    tenant_config.resourceName
route:     POST /api/tenant/resource/update
perm:      TENANT_ADMIN
namespace: unrestricted
egress:    unknown
severity:  high if full name controllable; medium if internal namespace only

降噪条件也是现成的。字符串常量的 lookup 直接压到底；名字来自只读部署配置的降一级；用户只控制逻辑 ID、服务端拼固定前缀并校验类型的降一级；出现 Context.OBJECT_FACTORIES、自定义 ObjectFactory 或自定义 InitialContextFactory 的提上来。

修复的三个层次

顺序我建议是设计层先收，代码层次之，运行时兜底。反过来的写法也很常见——先加 RASP，再补规则，最后才发现名字根本不该由用户给。

设计层就是不暴露 JNDI 名字，只暴露业务 ID，映射放在服务端。这一层做对，下面两层大多数时候用不上。

代码层是 allowlist 加类型校验：固定前缀、字符集和长度限制、失败不回退到原始输入、返回类型强校验、异常对外只说“资源不可用”。

运行时层管出口和依赖面。容器默认禁止访问外部 LDAP / RMI / IIOP，用 NetworkPolicy 或安全组把出站卡住；classpath 里别留用不上的 JNDI provider、JMS appender 和旧版 Log4j。

报告里我会这么写：

低权限租户管理员可修改资源配置字段 resourceName，该字段作为完整 JNDI 名称进入 InitialContext.lookup()。当前实现未限制命名空间、协议和返回对象类型。实际影响取决于运行时出口、JDK 版本和 classpath 中可用的工厂类；现有证据支持“可触发非预期 JNDI 访问与内部探测”，代码执行需要 classpath 里存在可被 Reference 触发的工厂类，这一点尚未验证。建议改为服务端维护 ID 到固定 java:comp/env/... 名称的映射，并补类型校验与出站限制。

比一句“可导致 RCE”啰嗦。但复核的人能顺着证据往下走，开发也知道该改哪一行。
