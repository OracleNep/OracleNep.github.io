一个网页几万字，真正要看的可能只是一个表单。把整页 HTML 喂进去，导航、脚本和重复页脚很快就占掉上下文；直接截断又不太放心，后面要查的东西可能刚好在被删掉的部分。

另一个麻烦藏在统计里。同一次模型请求，流上可能报好几次 usage。界面把每份数字都加上，看到的 Token 就比实际报告的多。连接中途断开时，如果又只在正常结束时记账，另一部分消耗反而不见了。

这两个地方分别改：工具返回的内容留一条回查路径，模型报告的用量按请求和轮次记。

网页先看摘要，原文留在会话里

WebFetch 现在会把原始 URL、最终 URL、跳转链、状态、耗时和正文信息一起返回。最常见的误判其实很直观：请求返回 200，打开却是登录页。保留最终地址和跳转链，至少能让 Agent 发现自己已经到了别的地方。

给模型的正文默认 8000 字符，可以设在 500–12000 之间。HTML 默认去掉导航、script、style 等噪声；需要看入口时，用 extract=true 提取表单、链接、脚本引用和注释。原文则保存在会话的 .research/http 下，通过 body_file 回去读。

原文也有上限，目前最多读取 2 MiB。所以返回字段特意叫 observed_body_bytes 和 observed_body_sha256：如果响应超过上限，长度和哈希对应的是读到并保存的那一段。正文摘要被截短、原始响应没读完，这是两件事，各有自己的标记。

请求出口也得固定。代理配置失败后自动直连，看起来像工具更“健壮”了，研究时却会添麻烦：前后响应变了，到底是参数有效，还是换了出口？当前实现会直接报配置错误。Shell 与 HTTP 工具按显式代理和 CA 配置工作，Windows 下还得认清实际跑的是 PowerShell 5.1，别把命令解析错误当成目标返回的结果。

40、65、65，最后该记多少

假设一次请求先后报了三份输出用量：40、65、65。这是累计快照的话，最后就是 65。逐条相加会变成 170。

收到的累计值   40    65    65
本次增加       40    25     0

usageDelta 对 input、output、cache read、cache write 分别保留本次请求见过的最大值，只把增加的部分交给观察器。重复快照不会再加一遍，数值暂时回退时也不会倒扣。

这里有个适配器约定：传进来的要是累计值。如果新 provider 给的是每块增量，先在适配层转换，不能直接套这个算法。光是字段名都叫 usage，并不能说明口径相同。

每轮有自己的观察器，子任务也单独记。汇总旧会话时则要照顾原来的累计快照，避免新轮次记录和旧 activity 重复相加。缓存读取单列出来，方便看长上下文有没有复用；要核账单，还得按具体 provider 的计费口径算。

流断了，已经收到的数字还在

usage 会先交给观察器，再把事件向外传。这意味着消费端中途停掉时，已经收到的用量仍能留下来。如果 provider 还没来得及发最后一份 usage 就断了，那一段也只能缺着，程序没法从半句文本反推出准确数值。

结束状态也一起收紧了。流读到 EOF，不足以说明模型正常结束；有些适配器还会在 EOF 时补一个结束事件。包装层要求实际的 StopReason，缺失时返回 ErrIncompleteRun。非流式调用也检查结束原因。

服务重启则处理另一种遗留：数据库里仍是 running 的执行和轮次会改成 interrupted，轮次原因记为 service_restart。下次打开会话，至少能知道上一次停在哪里，而不会一直看到“运行中”。是否续跑、从哪一步续跑，是接下来需要判断的事。
