01 / 上下文里应该保留可区分的信息

连续访问几个 URL，如果每次都把完整 HTML 塞进上下文，导航栏、脚本和重复页面很快会占满窗口。简单截掉长输出又会丢失回查能力：模型看到一段摘要，却无法确认它来自哪个最终地址、是否经历跳转、正文是否被截断。

prtseek 的处理是把一次 HTTP 访问拆成结构化观察、面向模型的有界正文和落盘原文。上下文优先保留能影响判断的字段；需要继续检查表单或脚本时，再读取对应材料。这种分层减少重复文本进入对话，但不会自动证明压缩后的信息足够完成所有任务。

02 / HTTP 200 只是观察中的一个字段

WebFetch 返回原始 URL、最终 URL、跳转链、状态、耗时、已读取响应长度、SHA256、截断标记和 body_file。一次访问最终落到登录页或验证页时，即使状态是 200，也应结合地址、正文与跳转链判断，不能直接记成“接口有效”或“目标达成”。

层次内容与当前边界用途
结构化元数据地址、状态、跳转、长度、哈希、耗时辨认请求实际到达哪里、结果是否变化
模型可见正文默认 8000 字符，可设置 500–12000控制单次观察进入上下文的体积
会话内原文.research/http，响应体最多读取 2 MiB按需复查与保留本次已读取内容

这里有两种截断：原始响应超过读取上限，以及展示正文超过字符预算。observed_body_bytes 与 observed_body_sha256 描述的是实际保存的字节；原始响应被截断时，它们只能标识保存下来的前缀，不能代表完整响应的长度或完整性。

HTML 默认过滤导航、script、style 等噪声；extract=true 会提取表单、链接、脚本引用和注释。默认摘要适合先判断页面性质，结构提取适合继续定位交互入口。两者都不能替代浏览器执行 JavaScript 后的实际行为。

03 / 网络出口也是实验条件

如果工具配置的代理失败后悄悄改用直连，前后两个响应可能来自不同网络路径。此时看到正文变化，很难判断是参数产生了作用，还是出口、证书或访问控制改变了结果。

当前 HTTP 工具使用显式代理与 CA 配置，配置错误会返回错误，不静默切换出口。Shell 和 HTTP 工具也应按一致配置解释网络行为。Windows 环境还需要识别实际 Shell：PowerShell 5.1、curl.exe、编码和脚本文件的行为，不能用 Bash 的命令习惯默认推断。

这意味着有些失败应先归入环境问题：证书加载失败、重定向异常或 Shell 参数解析失败，尚不足以反驳目标假设。把失败原因保留在观察记录里，可以避免 Agent 换一组参数继续重复同一个环境错误。

04 / 流式 usage 不能逐条相加

流式响应可能多次报告同一个请求的累计用量。假设输出 Token 快照依次为 40、65、65，正确的本次累计值是 65，直接相加却会得到 170。usageDelta 为 input、output、cache read、cache write 各自保留已见最大值，只累计正向差额。

本次请求的输出快照： 40 → 65 → 65
本次新增计量：       40 → 25 →  0
该请求累计输出：     65

next  = max(previous, current)
delta = next - previous

这个逻辑以 provider 适配层交出的累计 usage 为输入。如果新增适配器拿到的是逐块增量，必须先统一语义，否则最大值规则会漏计。不同协议的字段名称和计费定义也不能仅凭名称相近就认定一致。

每个 Chat turn 的观察器独立记账，子任务只共享预算。新轮次记录与旧会话累计快照的兼容汇总还要避免双算。缓存读取单列有助于解释上下文复用，但累计 Token 不等同于账单金额；未由 provider 报告的用量不能凭空补齐。

05 / EOF 不是正常结束信号

网络流断在半句回答后，如果适配层把 EOF 包成一个普通结束事件，上层就可能错误地把本轮记成完成。计量包装层因此要求看到真实的 StopReason；没有结束原因、也没有其他错误的流会被记为 ErrIncompleteRun。非流式返回同样检查结束原因是否存在。

usage 在事件向外传递前先进入观察器，因此中断前已经收到的用量可以保留下来。这不能恢复 provider 尚未发出的最后一份用量，但能避免因为消费者提前停止而丢掉已经观察到的数据。

服务重启后，仍处于 running 的执行和轮次会被修正为 interrupted，并记录 service_restart。这个修正表达的是“上一次运行未正常收尾”，不会暗示任务自动续跑或目标已经完成。前端也需要呈现结束原因，而不只是停止转圈。

06 / 减少上下文要保留回查路径

这一设计的取舍是把完整性、可读性与用量分开处理：模型看到的是有限观察，文件保留本次读取的原文，计量记录 provider 实际报告的数据。任何一层都不能借另一个层次的存在而夸大自己的保证。

验证这套机制应针对可确定的行为：累计快照不会重复相加、缺少结束原因会报错、截断标记与已保存字节一致、代理失败不会换出口。至于这些措施能减少多少 Token、能否提高任务成功率，需要在同一模型配置和任务集上做对照，不能从代码结构直接推导一个提升比例。
