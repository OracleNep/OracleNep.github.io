开机动画、主题，以及几个会话里的小问题

这轮前端改动从三个很直观的毛病开始：动画没了，默认黑色，弹窗和侧栏颜色对不上。后面又补了两个用起来才发现的。

这次的起点没什么技术含量：开机动画没了，默认主题变成黑的，对话框和侧边栏的色调也对不上。先把这三处改回来，再看会话操作里还有哪些地方别扭。

后面补的附件重试和文件预览属于另一类——平时注意不到，赶上发送失败或者快速切文件的时候，很难受。放在一起记。

首屏别先闪一下黑

默认主题设成 system 还不够。等 React 挂载再读偏好，首屏已经按深色画出来了，然后当着用户的面切成浅色。

现在主题脚本放在 head 里提前跑：读配置的 cookie 或 localStorage，解析 system，再把根节点的 dark class、主题属性和 colorScheme 设好。用户手动选过浅色或深色就继续尊重保存的选择；跟随系统是没明确偏好时的默认，不该每次刷新都替人重新决定。

颜色统一要往变量上收。聊天区、侧边栏、对话框各写死一套，主页面看着正常，弹窗一开就露馅——尤其是 portal 出去的弹层，别指望它一直继承某个局部容器的样式。检查的时候把设置、菜单、文件预览都打开，边框和文字一起看。

开机动画怎么收场

动画每次 document load 播一次。刷新会重播；应用内切会话时，只要布局没卸载就不会再来一遍，这个行为是对的。

实现用了原生 <dialog>，hydration 之后调 showModal()。选它主要是为了键盘焦点：普通遮罩铺得再高，按 Tab 还是可能摸到后面的输入框。画面既然在播启动动画，交互就该待在前面。

关闭有两个来源：动画结束事件，和计时器兜底。普通模式两秒左右，系统要求减少动态效果时缩到 600 毫秒；中间留着跳过和 Esc。CSS 动画被打断时，计时器还能把它收掉。开场可以有存在感，但别让人等不到输入框。

文件传过了就别再传

上传附件和发消息是两次操作。前面成功、后面失败，如果直接重跑整个 send，文件就又传一份。

uploadChatFiles 现在保留成功上传的回执。重试时先对着当前 File 对象找，有回执的直接用，没有的再传。于是 A、B 都传成功、消息没发出去之后，再点发送只重试消息；留着 A 的回执又加了 B，也只补 B。

这还不是断点续传。少文件是成批传的，整个请求失败或者回执数量对不上，不能逐个恢复这一批的进度。也没做内容哈希去重：刷新页面、重新选文件之后，不能假设还能命中旧回执。现在修的就是“明明传过了，因为消息失败又传一遍”这一个。

点 B 显示 A

先打开 A，马上切到 B。B 的请求先回来，A 后回来，两边都直接写 state 的话，屏幕上显示的还是 A。网慢的时候特别容易看错材料。

预览现在带一个递增的 previewRequest 版本号，只有仍然对应当前版本的响应才能改内容；关对话框也递增，让晚到的响应作废。请求没被取消，但它已经没有权限改掉当前选择。

会话概览补了几个直接显示的东西：结束原因、目标状态、累计 Token、缓存读取，还有仍在活跃的子任务。文件列表区分 input、artifact 和 evidence——看结果时能分清这是上传的题目、生成的脚本，还是实际验证材料，省掉不少翻聊天记录的时间。

上传这块离断点续传还差得远，先这样。
