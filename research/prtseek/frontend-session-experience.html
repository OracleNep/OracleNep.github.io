01 / 长任务界面需要回答具体问题

一次 Agent 任务可能同时有模型输出、多个子任务、附件上传和文件产物。用户最需要知道的是：现在还在运行吗，哪条路线卡住了，附件是否已经上传，结果文件属于哪次操作，当前结论验证到什么程度。

如果界面只显示聊天气泡和一个停止按钮，这些信息就只能靠用户从文字里猜。prtseek 的前端改动既包括恢复启动动画和统一主题，也包括把运行状态、目标状态、用量与文件归属放到可观察的位置。视觉一致性和状态准确性需要一起验收。

02 / 系统主题要在首屏就生效

默认跟随系统，首先意味着没有显式用户偏好时使用 system。用户已经选择浅色或深色后，仍应尊重保存的值。主题启动脚本在 head 中提前读取配置的 cookie 或 localStorage，将 system 解析为当前系统颜色，并设置根节点的 dark class、主题数据属性和 colorScheme。

提前执行的作用是减少 hydration 前后的主题闪烁。如果等 React 挂载后才纠正默认深色，浅色系统也会先看到一次黑屏。保存偏好、首次访问、存储不可用与非法偏好值，都应有可解释的回退行为。

对话框和侧边栏的一致性依赖语义颜色：background、foreground、sidebar 等变量应随当前主题一起解析。弹层通常通过 portal 渲染到页面其他位置，局部容器里写死的颜色更容易失效。因此检查主题不能只看聊天主体，还要打开设置、文件预览、菜单和侧边栏比较文字、边框与底色。

03 / 启动动画也要处理焦点和退出

PrtsBoot 在每次 document load 播放一次。应用内导航如果没有卸载布局，就不会反复播放；刷新页面会再次出现。这个边界比持久化一个“永远不再播放”的标记更符合启动动画的含义，也避免每次切换会话都阻挡操作。

动画使用原生 <dialog>，在 hydration 后调用 showModal()。单纯盖一层高 z-index 遮罩，只能挡住鼠标视线，键盘焦点仍可能落到后面的输入框；模态 dialog 则把启动阶段的交互边界交给浏览器处理。

退出由动画结束事件和计时兜底共同保证，普通模式约 2000 毫秒，减少动态效果模式约 600 毫秒，同时支持跳过与 Esc。测试不能只录一段动画顺利播完，还应覆盖动画事件没有触发、用户立即跳过、键盘退出和 reduced motion。启动装饰一旦阻塞输入，就变成了可用性故障。

04 / 发送失败，不应该重传已成功的附件

附件上传与消息发送是两个步骤。上传成功后，模型请求或消息提交仍可能失败。如果重试把整组文件重新上传，既浪费时间，又容易在工作区制造重复材料。uploadChatFiles 保存成功上传的回执，重试时复用已有回执，只上传缺少回执的附件。

合成示例：选择 A、B 两个文件
第一次：批量上传成功 → 保存 A、B 回执 → 消息发送失败
第二次：复用 A、B 回执 → 直接重试发送消息

如果保留 A 回执后新增 B：只上传尚无回执的 B

当前复用基于 File 对象引用。它解决的是同一轮界面操作中的重复上传，不是内容哈希级的全局去重。重新选择文件、刷新浏览器或换一台设备，都不能据此假定会自动命中之前的回执。

还要区分“已有回执”与“服务端可能收到了部分字节”。缺失附件以一个批次上传；如果整个请求报错，或回执数量与文件数量不一致，函数不会承诺保存这个失败批次的逐文件进度。现有机制覆盖上传成功后发送失败的复用，不是断点续传。测试既要检查回执复用与顺序，也要检查上传报错后草稿仍可重试，不能只看最终附件数量。

05 / 晚到的预览不能覆盖当前选择

用户先打开文件 A，马上切到 B；如果 A 的响应比 B 晚到，缺少保护的界面会显示 A，却仍让用户以为自己在看 B。会话概览用递增的 previewRequest 版本标识请求，只有当前版本的响应可以更新预览。关闭 dialog 时也递增版本，让尚未返回的旧请求失效。

版本校验解决的是界面状态竞争，不等于已经取消底层网络请求。两者都可能有价值，但不能把防止旧响应覆盖写成“没有多余请求”。文件列表还区分 input、artifact 和 evidence，让用户知道所看的是原始附件、生成产物还是验证材料。

这些细节直接影响判断：如果一个旧文件预览覆盖了新实验结果，用户很容易把过时观察当成当前证据。把响应归属写进状态更新条件，比仅依靠加载动画更可靠。

06 / 概览展示状态的来源与边界

概览把 execution、outcome、耗时、累计 Token、缓存读取、结束原因、共享调用数和活跃子任务分别展示。用户可以同时看到“运行已结束”和“目标仍未验证”，也可以知道是服务重启、取消还是其他异常导致本轮终止。

验证等级旁注明 Agent 报告，避免把模型提交的结论呈现成平台裁决。标签、颜色和文字都应沿用同一状态含义：不能仅因运行 completed 就显示一个暗示验收成功的总状态。

前端验收因此包含两类检查。一类是不同屏幕和主题下的可读性、弹层与键盘操作；另一类是故障状态下的信息准确性，包括上传重试、快速切换预览、子任务未结束和服务重启。漂亮的正常态截图只能覆盖其中一部分。
