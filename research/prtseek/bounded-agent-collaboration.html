01 / 派发完成，只代表任务已启动

同步派发很容易让父 Agent 卡在最慢的子任务上。prtseek 的 delegate_agents 改为启动子任务后立即返回会话编号，父 Agent 可以继续检查材料，再通过 wait_agents 收取结果。这使协作从一串嵌套调用变成需要显式管理的任务集合。

异步带来的第一个陷阱，是把派发回执当成任务结果。另一个陷阱是等待所有路线完成才做判断：某个 solver 已经给出足够强的证据，其余路线仍可能继续消耗调用。当前等待逻辑在有新的终态结果时即可返回，并告诉父任务是否还有 pending 工作，让父任务有机会调整下一步。

等待超时也不代表子任务失败。wait_agents 的单次等待窗口是 1–30 秒，默认 20 秒；窗口结束可以返回仍在运行的任务。任务自身的截止时间、整个工作流的取消与一次轮询超时需要分别处理。

02 / 上限约束整棵任务树

同时活跃的子任务8 个限制并发资源占用

派发深度上限4限制递归协作层次

这些数字是本文源码快照里的默认实现值，不是评测得到的最优参数。尤其是单次派发，实现接受 1–6 个任务；旧说明中出现过 2–6 的文字，阅读时应以当前工具校验为准。允许一个任务，可以避免为了满足“多 Agent”形式而人为制造重复路线。

并发数、任务总量和深度必须同时约束。只限制活跃数，仍可反复创建新任务；只限制深度，浅层也能扩张出大量分支。计数检查与更新在工作流锁内完成，启动失败时回退预留计数，避免失败派发永久占住名额。

03 / 共享预算，独立归账

父子任务通过 context 继承同一个 RunBudget 指针。调用 provider 前，预算用原子 CAS 预留一次额度，避免多个并发执行者都看见“还剩一次”并同时越过上限。下面是机制示意，不是源码原文：

repeat:
    used = atomic_load(shared.used)
    if used >= limit: return budget_exhausted
    if compare_and_swap(shared.used, used, used + 1):
        break
invoke_provider()

预算约束的是逻辑模型请求，包括压缩与继续生成时触发的请求；底层网络重试还有独立限制。它既不等同于 Token 上限，也不等同于 HTTP 请求总数。把这三个口径混在一个“调用次数”里，会让调试成本和费用解释都变得困难。

共享总量不意味着共享每轮计量器。每个 Chat turn 安装独立的 ModelObserver，将自己的用量记到自己的轮次；父子树的汇总由上层完成。这样既能限制整轮开销，又能看到资源实际花在哪个子任务，避免子任务用量同时进入父、子账本后再被重复相加。

04 / 完成状态还需要被父任务收取

子任务结束后，结果并不会天然进入父 Agent 的上下文。运行时保留 delivered 标记，区分“已经产生结果”和“父任务已经收取结果”。completionCheck 会检查直属子任务是否仍在运行，或存在尚未收取的终态结果；若有，就要求先等待、取消并收取，再结束交付。

例如 A、B 两条路线同时运行，A 找到候选并校验成功，B 正在重复读取同一份材料。父任务可以收取 A，判断 B 已无必要，再请求取消 B，最后等待 B 的终态。这最后一步提供了可确认的关闭边界，不能用“取消请求已发送”替代。

cancel_agent 的范围限定为本轮直属子任务及其后代，不能随意停止另一棵任务树。子任务之间的证据也要带会话归属，避免把一个真实编号放进错误任务后仍被当成有效引用。

05 / 关闭顺序保护下一轮会话

用户可能在上一轮结束后马上追问。如果旧子任务还在写 transcript，而新一轮已经开始使用同一会话资源，就会出现跨轮写入或状态错配。关闭工作流因此采用明确顺序：先标记 closed 阻止继续派发，再取消运行上下文，最后通过 WaitGroup.Wait() 等待子任务退出。

子任务自身结束时也会取消并等待直属后代，再释放自己的 busy 标记。运行状态判断则读取继承的运行上下文和取消原因，避免把清理阶段主动发出的取消误记成用户取消，覆盖原本正常完成的结果。

这依赖工具执行链尊重取消和超时。关闭逻辑本身不能强迫任意不响应 context 的外部程序立即结束；如果未来增加新的工具适配器，需要同时验证它的终止行为。生命周期设计的价值在于把这一要求放到明确位置，而不是假定所有 goroutine 都会自行退出。

06 / 并行收益来自互补信息

比较单 solver 与 command 工作流时，至少应同时观察目标完成、错误报成功、总用量、耗时和重复调用。单纯看到墙钟时间变短，还不足以说明更划算；如果重复读取和汇总成本上升，短任务甚至可能更适合串行。

下一步值得做的是按任务类型比较路线互补性，而不是直接增加并发上限。当前实现首先保证派发可追踪、预算有上限、结果会被收取、取消有结束边界。是否提高真实模型的解题表现，需要独立评测回答。
