多 Agent 里最显眼的功能是同时启动几个 solver。写到后面会发现，需要反复处理的反而是收尾。

设想 A、B 两条路线一起跑：A 已经给出了可用结果，B 还在继续尝试。父 Agent 能不能先交付？如果不需要 B 了，按下取消之后是不是就能开始下一轮？这些问题不处理，页面上看起来已经结束，后台却可能还在请求模型、写会话记录。

prtseek 的 delegate_agents 启动后立即返回子会话编号，之后用 wait_agents 收结果。这样父任务不用堵在派发调用里，但也多了一份责任：记住自己派出了什么，以及哪些结果还没有拿回来。

子任务结束了，父任务未必知道

这里有一个不太起眼的字段：delivered。它记录父任务有没有收取结果。子任务进入终态，只能说明结果已经产生；父 Agent 的上下文里可能还没有这份结果。

wait_agents 看到新的终态结果就可以返回，同时给出是否还有 pending 任务。它不用等所有路线都跑完。一次等待默认 20 秒，允许设成 1–30 秒；等到超时仍然可以返回“还有任务在跑”，这个超时不负责判定子任务失败。

父任务准备结束时，completionCheck 会再看一遍直属子任务。仍在运行的要处理，已经结束但没收取的也要处理。这样能挡住一种很别扭的交付：子任务明明找到了结果，父任务却因为没拿到它，还在按旧判断写最终回答。

取消之后还要等一下

回到 A、B 的例子。收取 A 以后，如果 B 已经没有继续跑的必要，就调用 cancel_agent，然后再 wait 一次，把 B 的最终状态收回来。取消请求返回时，工具可能正在退出，不能把“已经通知停止”当成“已经停止”。

取消范围限于本轮直属子任务及其后代。整轮关闭时，代码先把工作流标记为 closed，挡住新派发，再取消 context，最后等 WaitGroup。这几步的顺序不能随便换：用户下一句话进来之前，上一轮的 transcript writer 得先收干净。

还有一处容易把状态记错。子任务正常返回后，清理代码自己也会发取消信号。如果直接看清理后的 context，就可能把正常完成记成 cancelled。当前实现会区分运行期间的取消和收尾时的取消，并在释放 busy 标记之前等待后代退出。

这一套仍然依赖工具愿意响应取消。新接进来的外部程序如果完全不理会 context，就得另外解决进程终止，光等 goroutine 不会让它自己消失。

预算不能按人头各发一份

父任务允许 200 次调用，子任务再各允许 200 次，派发几层以后，总开销就和最初的限制没什么关系了。现在父子通过 context 共用一个 RunBudget，调用 provider 之前先预留额度。

预留用原子 CAS。假如只剩一次，两个 solver 同时过来，只有一个能拿到它。这里数的是逻辑模型请求，压缩上下文和 continuation 也算；provider 内部的网络重试另有限制。它控制不了每次请求有多长，因此不能拿调用预算代替 Token 预算。

任务数量也有几道限制：单次派发 1–6 个 solver，同时活跃的子任务最多 8 个，本轮累计最多 24 个，派发深度上限 4。并发数管住眼前的资源，总量则挡住“结束一个再创建一个”不断往下跑。这些是当前代码里的设定值，还没有理由把它们说成最优配置。

共享额度和记账还得分开。每个 Chat turn 用自己的 ModelObserver 记录用量，之后再汇总父子任务。否则子任务消耗先计入父任务、又在汇总时加一次，数字会越算越大。

有时一个 solver 就够了

允许单次只派一个 solver，是为了不给简单题硬凑第二条路线。两个人都去读同一个文件、试同一种解法，最后还得多花一轮合并结果，这种并行未必划算。

我更想看到的对照是：多花的调用，究竟换来了哪条原本没有的证据。耗时可以一起看，错误报成功的次数也要看。现在先把任务能停下来、结果能收回来这两件事做实，继续加并发之前，再用具体题目判断值不值。
