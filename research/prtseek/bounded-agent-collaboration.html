多 Agent 最显眼的功能是同时开几个 solver。真写起来，反复改的其实是收尾。

设想 A、B 两条路线一起跑：A 已经给出可用结果，B 还在试。父 Agent 能不能先交付？如果 B 不要了，按下取消是不是就能开下一轮？这些不处理，页面上看着结束了，后台还在请求模型、还在写会话记录。

prtseek 的 delegate_agents 启动后立刻返回子会话编号，结果用 wait_agents 收。父任务不用堵在派发调用里，代价是多一份账要记：自己派出了什么，哪些结果还没拿回来。

delivered 这个字段

我一开始以为子任务进终态就等于结果到手。不是。终态只说明结果产生了，父 Agent 的上下文里可能还没有它。

所以单独记了一个 delivered：父任务有没有真的把结果收走。

wait_agents 看到新的终态就返回，顺手告诉你还有没有 pending。它不等所有路线跑完——一次默认等 20 秒，可以设 1–30 秒；等超时了也照样返回“还有任务在跑”，这个超时不负责判定子任务失败。

父任务准备收工时，completionCheck 再把直属子任务看一遍。还在跑的、已经结束但没收的，都要处理。挡的是一种很别扭的交付：子任务明明找到了结果，父任务没拿到，还在按旧判断写最终回答。

cancel 之后还要等一下

回到 A、B。收下 A 之后，如果 B 没必要继续，就 cancel_agent，然后再 wait 一次，把 B 的最终状态拿回来。取消请求返回时，工具可能还在退出，“已经通知停止”和“已经停止”是两件事。

取消范围限于本轮直属子任务和它们的后代。整轮关闭的顺序是先给工作流打 closed、挡住新派发，再取消 context，最后等 WaitGroup。这几步不能换：用户下一句话进来之前，上一轮的 transcript writer 得先收拾干净。

有一处容易把状态记错。子任务正常返回后，清理代码自己也会发一次取消信号；直接看清理后的 context，正常完成会被记成 cancelled。现在的实现把运行期间的取消和收尾时的取消分开，并且在释放 busy 标记之前等后代退出。

这套东西依赖工具愿意响应取消。新接进来的外部程序如果完全不理会 context，只能另外做进程终止——光等 goroutine，它不会自己消失。

RunBudget 挂在 context 上

父任务允许 200 次调用，子任务再各给 200 次，派几层之后总开销就和最初的限制没关系了。

现在父子通过 context 共用一个 RunBudget，调 provider 之前先预留额度。预留是原子 CAS：只剩一次的时候两个 solver 同时来，只有一个拿得到。

这里数的是逻辑模型请求，压缩上下文和 continuation 也算在内；provider 内部的网络重试另有限制。它管不了每次请求多长，所以调用预算替代不了 Token 预算。

任务数量另有三道闸：单次派发 1–6 个 solver，同时活跃的子任务最多 8 个，本轮累计 24 个，派发深度 4 层。并发管眼前的资源，总量挡的是“结束一个再起一个”慢慢往下跑。这些是当前代码里的数，没什么理由说成最优。

共享额度和记账得分开。每个 Chat turn 用自己的 ModelObserver 记用量，最后再汇总父子。混在一起会出另一种错：子任务的消耗先算进父任务，汇总时又加一遍，数字越滚越大。

有时候一个 solver 就够了

单次允许只派一个，是不想给简单题硬凑第二条路线。两个人读同一个文件、试同一种解法，最后还要多花一轮合并结果，这种并行是负收益。

我更想看另一组对照：多花的这些调用，换回了哪条原本拿不到的证据。耗时一起看，错误报成功的次数也一起看。现在先把“停得下来、收得回来”做实；再加并发之前，拿具体题目说话。
