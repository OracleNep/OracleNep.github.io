仓库里有条命令很容易只看前半截：

go test ./... -run '^$'

./... 覆盖所有包，-run '^$' 一个用例都不跑。它在这里干的是编译检查。把这一行绿了说成“全量测试通过”，就是把两件事混成一件。

整理验证流程的时候，我想把这个区分说明白：CI 要说清楚检查了什么，评测结果也要能追回实际跑过的东西。下面分开写。

流水线跑了什么

原生构建跑 Ubuntu、macOS 和 Windows。编译所有包之后，agent/server 按指定模式执行 CTF 工作流、capture、计量、HTTP 观察和研究记录几组回归，再跑 db/config。前端装依赖、跑测试，最后做静态构建。

没把历史全量测试直接摊到三个平台上，是因为里面还有些跟平台相关的 Shell fixture 和后台任务时序用例。当前选的范围写在 workflow 里，看结果也只能按这个范围理解。

之前还删掉了不稳定的 unused dependency audit。检查器本身不可靠，要修的是检查器；去掉之后，它原来盯的依赖问题仍然得在依赖变更时人工过一遍。构建、核心回归、冒烟这些保留。

交付物还得再往前走一步。Next.js 静态导出成功，不代表 Go 二进制里把资源装对了，所以有 embedui 路由测试和真的启动冒烟。容器另外查 Compose 配置、构建、健康状态、替换和数据持久化——能 build 出来，和换一次容器之后数据还在，得分开试。

三道小题

scripts/eval-ctf.py 里现在是三类合成材料：字节 XOR、带诱饵候选的压缩包、缺少必要附件的任务。

压缩包题不许见到 flag 形状的字符串就收工，得按校验文件找到唯一匹配项。缺附件那题要求报 blocked，不许编一个答案。这种用例很有必要：如果所有题都设计成“继续试就能成功”，根本测不出 Agent 会不会在材料不够时停下来。

评分上，已知答案题要求输出里的 flag 集合恰好等于预期、outcome 是 verified、证据集合非空；缺材料题要求 blocked，且回答里没有虚构的 flag。false_success 单独记，数的是自称验证成功却没通过判定的情况。

脚本有两个入口，名字容易混：

python scripts/eval-ctf.py --self-test
python scripts/eval-ctf.py --dry-run

前者检查合成材料和评分规则，后者列出计划跑的题目、模式和规模。两个都不调模型。真要跑 single solver 和 command 的对照，得准备隔离的本地实例、模型配置和认证信息，还会消耗实际额度。

多花的调用换来了什么

实际运行会记通过情况、false_success、模型调用数、输入输出 Token、耗时和工具调用。完全重复的调用也算进去，等结果这类轮询排除掉。

我会先看错误报成功，再看耗时和用量。多 Agent 快了一点、却在缺材料时更容易硬凑答案，这个结果就不该只拿平均耗时来说话。反过来，多花了调用但补上了原本没有的校验，也值得单独看。

这三道小题只能查基本流程，题目太少也太简单。要比模型能力，得固定模型、参数、版本和预算，用不同类型的题重复跑。现在的精确重复计数，也抓不住“换个参数做同一件事”。

这里没有一份新的真实模型对照成绩。CHANGELOG 里的测试数是当时那次验证留下的，写这篇文章时没有重跑完整矩阵。以后要写“解题率提高了多少”，得先有对应题集和运行记录，不能从这几个 PASS 往外推。
