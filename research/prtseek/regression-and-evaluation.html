01 / 稳定运行和更会解题，需要不同证据

修复一次流中断误判，可以通过确定性输入验证：喂给包装层一个没有结束原因的流，检查它是否返回不完整运行错误。判断多 Agent 是否比单 solver 更会解题，却不能靠同样的测试得到答案；那需要真实模型、可比较的题集和重复运行。

prtseek 的验证应分层阅读。编译检查回答代码能否构建，回归测试回答已知路径是否符合约束，冒烟检查回答最终程序能否启动并提供功能入口，评测才进一步比较任务结果与资源消耗。跨过一层，就需要相应的新证据。

02 / 当前 CI 实际执行的范围

检查当前工作流能够支持的判断
后端编译go test ./... -run '^$'所有包及测试代码可编译，不代表执行全部测试
后端回归agent/server 指定模式；db/config 测试所选 CTF、计量、HTTP、研究记录等行为得到检查
前端npm ci、npm test、静态构建依赖安装、指定测试与导出流程可完成
原生交付Ubuntu、macOS、Windows；embedui 路由及启动冒烟构建后的程序可提供被检查的工作台入口
容器交付Compose 校验、构建、健康状态、替换与持久化冒烟被覆盖的容器生命周期符合预期
评测工具自检eval-ctf.py --self-test合成材料与评分规则符合脚本的确定性断言

历史全量测试包含平台相关 Shell fixture 和后台任务时序用例，因此当前工作流选择了明确的回归范围。这里应如实写出选择，不能把“编译所有包”描述成“全部历史测试已在三个平台执行”。

同样，检查器本身也需要可靠。移除不稳定的 unused dependency audit 后，仍需保留构建、核心回归与冒烟，并通过依赖变更审查补充判断。一次检查变绿只说明当前门禁通过，不自动证明被移除检查关注的问题已经消失。

03 / 检查实际交付物，而不只看源码

前端能静态导出，不代表 Go 二进制已经嵌入正确资源；容器能构建，也不代表重建后数据还在。于是 embedui 路由检查和程序冒烟直接面向构建产物，容器测试进一步覆盖健康状态、替换与持久化。

这类测试适合捕捉跨层故障：导出目录复制错误、平台启动脚本差异、路由缺失、持久化路径配置错误。它们不需要让模型真正解一道题，也不应依赖个人部署的历史会话才能执行。

验证数据应在隔离目录中生成，报告只保留判定所需内容。复现某个私有会话的问题时，也要把可公开的故障条件整理成最小合成用例，避免把聊天记录、数据库或目标地址提交进仓库。

04 / 三类小题，分别检查三种行为

scripts/eval-ctf.py 生成三类本地材料：字节 XOR、带诱饵候选的压缩包，以及明确缺少必要附件的任务。它们规模很小，目的在于检查读取、校验和诚实报告阻塞的基本流程。

已知答案题要求输出中的 flag 集合恰好等于预期、outcome 为 verified，且证据集合非空。缺材料题要求 blocked 且不输出虚构 flag。脚本还记录 false_success，用来识别自称 verified 却未满足评分条件的运行。

# 无凭据的材料与评分规则自检
python scripts/eval-ctf.py --self-test

# 只列出合成题、模式与运行规模，不调用模型
python scripts/eval-ctf.py --dry-run

self-test 验证的是生成器和评分规则；dry-run 展示配置。二者都不会给出真实模型解题表现。实际执行需要隔离的本地实例、选定模型配置和认证信息，并会产生模型调用成本。不能把 self-test 的 PASS 写成 Agent 已经完成了这些题。

05 / 对照结果要同时看正确性和开销

实际评测可以分别运行 single solver 和 command 工作流，记录通过情况、错误报成功、模型调用、输入输出 Token、耗时、工具调用及完全重复的调用。轮询类操作不应因为次数多就被算成无效探索。

当前重复调用指标偏向精确匹配，无法识别所有“参数不同、语义相同”的尝试；通过条件也只面向这几道合成题。即使某配置全部通过，也不能推出它在未知比赛题型上有同样成功率，更不能仅凭一次运行判断多 Agent 优于单 Agent。

更有说服力的后续比较需要固定模型与参数、记录版本和预算、重复运行，并按题型展示失败类型。若多 Agent 用量显著增加却没有减少错误报成功，这个变化就不应只用平均耗时的改善来宣传。对材料不足的任务，准确报告 blocked 本身就是需要计入的正确行为。

06 / 让每个结论对应一种验证

这个系列基于固定源码快照分析机制，没有在撰写期间重新执行完整 prtseek 测试矩阵或真实模型对照。仓库 CHANGELOG 中的历史测试数量属于对应提交的验证记录，不应挪作本次文章发布的新结果。

可以从代码与确定性测试讨论的，是共享预算如何预留、证据引用如何校验、缺少结束原因如何处理，以及最终交付物检查了哪些入口。至于稳定性提升幅度、费用下降比例和解题率变化，应由对应实验报告支持。

后续版本继续补充文章时，值得记录触发问题、变更机制、验证方法和剩余限制。这样读者可以沿着提交与测试复查工程判断，而不是只看到一串“优化完成”的更新标题。
