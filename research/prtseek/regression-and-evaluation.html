仓库里有一条命令，很容易只看前半截：

go test ./... -run '^$'

./... 覆盖所有包，但 -run '^$' 不执行普通测试用例。它在这里承担的是编译检查。如果把这一行绿了写成“全量测试通过”，就把两件事混在一起了。

整理 prtseek 的验证流程时，我想把这个区别说明白。CI 需要检查具体行为，评测结果也得能追到实际跑过的东西。

现在这套流水线查哪些地方

原生构建跑 Ubuntu、macOS 和 Windows。编译所有包之后，agent/server 按指定模式执行 CTF 工作流、capture、计量、HTTP 观察和研究记录等回归，再跑 db/config。前端安装依赖、执行测试，然后做静态构建。

没有把历史全量测试直接塞进三个平台，是因为里面还包含平台相关的 Shell fixture 和后台任务时序用例。当前选择的范围写在 workflow 里，读结果时也只能按这个范围理解。

之前还移除了不稳定的 unused dependency audit。检查器如果本身不可靠，就得处理检查器；去掉以后，它原来关注的依赖问题仍要在依赖变更时审查。构建、核心回归和冒烟这些检查继续保留。

交付物还要再往前走一步。Next.js 静态导出成功，Go 二进制里也可能没装对资源，所以有 embedui 路由测试和实际启动冒烟。容器则另外查 Compose 配置、构建、健康状态、替换和数据持久化。能 build 出来，和换一次容器后数据还在，得分别试。

三道小题，也包括一道做不出来的

scripts/eval-ctf.py 里现在有三类合成材料：字节 XOR、带诱饵候选的压缩包，以及缺少必要附件的任务。

压缩包题不能见到 flag 形状的字符串就收工，要按校验文件找到唯一匹配项。缺附件那题则要求报告 blocked，不能编一个答案。这种用例很有必要，不然所有题都安排成“只要继续尝试就能成功”，测不出 Agent 会不会在材料不足时停下来。

评分时，已知答案题要求输出里的 flag 集合恰好等于预期，outcome 为 verified，而且证据集合非空。缺材料题要求 blocked，回答里没有虚构 flag。另外单独记 false_success，统计自称验证成功却没满足判定的情况。

脚本有两个容易混淆的入口：

python scripts/eval-ctf.py --self-test
python scripts/eval-ctf.py --dry-run

前者检查合成材料和评分规则，后者列出计划运行的题目、模式和规模。它们都不调用模型。真正跑 single solver 和 command 对照，需要隔离的本地实例、模型配置和认证信息，也会消耗实际调用额度。

多花的调用换来了什么

实际运行会记录通过情况、false_success、模型调用数、输入输出 Token、耗时和工具调用。完全重复的调用也会统计，等待结果这类轮询则排除掉。

我会先看错误报成功的情况，再看耗时和用量。如果多 Agent 快了一点，却在缺材料时更容易硬凑答案，这个结果不能只拿平均耗时出来说。反过来，多花了调用但获得了原来缺失的校验，也值得单独看。

这三类小题只能帮忙查基本流程，题目太少，也太简单。比较模型能力还要固定模型、参数、版本和预算，重复跑不同类型的任务。当前的精确重复计数，也抓不住所有“换一种参数做同一件事”的情况。

这里没有一份新的真实模型对照成绩。CHANGELOG 里的历史测试数属于当时那次验证，写文章时也没有重跑完整矩阵。后面如果要写“解题率提高了多少”，得先有对应题集和运行结果，不能从这几个 PASS 往外推。
