01 / 参数在变化，结果可能没有变化

一个常见的停滞场景是连续修改请求参数，却反复得到同一张验证页。工具调用都成功返回，Agent 也不断解释下一种可能性，但有效信息没有增加。若只数调用次数，这段过程看起来很忙；若比较观察结果，就能发现路线没有推进。

另一个场景是旧文件污染：上一轮已经生成了 result.txt，新一轮脚本失败，随后读取旧文件仍然得到预期文本。如果把“文件存在”当成验证，失败就会被包装成复现成功。prtseek 的改动分别从阶段复核和实验材料归属处理这两个问题。

这里需要的记录是当前假设、支持证据、反证和下一项可区分变量。让 Agent 再写一段更长的自我解释，并不能取代一次新的观察。

02 / 阶段复核是软提示

运行时保留最近 8 次非轮询工具调用的观察。相同结果出现至少 3 次，或窗口内失败至少 4 次，会触发停滞候选；检查还设有至少 4 步的间隔，并在每 8 步安排常规复核。这样可以减少连续重复提醒，同时保留主动检查的机会。

对 HTTP 观察，比较签名采用状态、已读取正文长度、哈希与原文截断标记，排除耗时和临时产物路径等变化字段。这样不同参数得到相同响应时，不会因文件名变化而被误认成新结果。其他工具输出按原文计算签名，避免模糊文本匹配把不同观察压成一类。

触发后，系统加入阶段复核提示，并在有证据引用时尝试保存检查点。它不会自动封锁工具、额外请求模型或启动新 Agent。相同响应有时正是稳定性实验需要的结果，因此这只是提醒执行者重新判断，不是自动宣布路线错误。

这一规则也有盲区：带随机字段的相似响应可能绕过精确比较，两个语义不同的实验也可能得到相同正文。它的用途是发现值得复查的迹象，不能替代语义分析。

03 / 实验开始前就定义预期观察

research_experiment 要求提供 hypothesis、changed_variable 和 prediction，分配唯一的 exp-… 编号、实验目录和产物前缀。先描述改变了什么、预期看见什么，可以让失败与反证有明确位置，而不是得到任意输出后再为它寻找解释。

合成实验设计（字段示意）
hypothesis       = 新脚本能把本地输入转换为预期结果
changed_variable = 只替换转换函数，其余输入保持一致
prediction       = 本实验独有的输出文件出现，内容通过校验

基线：确认本实验输出尚不存在，记录输入校验值
执行：把输出写入新分配的实验目录
结果：读取新文件并验证内容，引用新的工具观察

独立目录减少本地同名产物残留的干扰，但不会重置远端缓存、会话状态或服务端文件。涉及远端状态时，仍需唯一标识或经过验证的复位，并先记录基线。重新读取一次旧文件，最多说明旧观察可再次读取，不能证明重新执行也得到了相同结果。

当前校验能确认实验编号和目录存在，能确认基线观察早于结果观察；它不能从两段任意工具输出中证明实验只改变了一个变量。这一部分仍由实验设计和证据审阅承担。

04 / 把验证等级写进报告

等级含义报告需要表达什么
inference推断假设与依据；不能把仅推断的目标标为 verified
observed实际观察验证说明与真实工具证据
reproduced独立复现的报告实验编号、本会话不同且按时间顺序的基线与结果证据
accepted平台接受的报告接受证据，并把它同时列入 evidence 集合

目标状态与验证等级也不是一个字段。partial 可以带实际观察，表示某一环节得到支持，但整体验收尚未满足；verified 则要求验证说明及成功的实际工具观察。派发回执、等待结果、研究记录或旧报告本身，不作为完成目标的独立成功观察。

accepted 的名字尤其容易造成误读。系统要求引用实际成功工具观察，但没有因此变成通用平台判题器。必须检查该观察的内容是否真的包含对应目标的接受结果。前端使用“验证等级 · Agent 报告”的表述，就是为了保留这一归属。

05 / 证据校验首先解决身份与完整性

证据引用包含会话编号与观察编号。校验首先确认引用属于当前任务或其后代，再确认观察记录存在、文件可读、大小和 SHA256 与记录一致。这样可以拒绝编造编号、越过任务归属的引用，以及记录后被改写的证据内容。

复现等级进一步要求基线和结果来自本会话、使用不同观察编号、基线先于结果，且实验由 research_experiment 创建。平台接受等级则要求 acceptance_evidence 同时出现在总证据集合中，避免报告标题与实际引用脱节。

产物使用会话工作目录内的相对路径，必须指向现存普通文件。存在一个脚本，和脚本曾成功执行，是两种证据；存在一份结果文件，和内容满足题目条件，也是两种证据。产物清单不能替代验证观察。

06 / 字节完整性之后，还有语义验收

假设一个工具成功输出了字符串，证据文件未被修改，引用归属也合法。系统可以据此确认“这次观察确实存在”。它仍不能仅凭哈希判断字符串是否是正确答案、是否来自本次实验，或是否对应当前题目的验收条件。

因此，继续优化时值得引入针对具体任务的确定性校验器，例如校验合成题的唯一候选、文件格式或程序退出结果，并把校验器的输入和输出纳入证据。通用报告结构负责把材料组织起来，任务专用校验负责回答具体命题，两者需要通过真实观察连接。

当前机制降低了“只有一句成功声明”的接受空间，也让失败更容易复盘。它提供可复核结论的基础条件，尚不足以保证每个 Agent 报告在语义上都正确。
