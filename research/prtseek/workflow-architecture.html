把 prtseek 改成一个 CTF 工作台

题目附件落在哪，派出去的任务怎么收尾，找到的字符串算不算答案。这三件事比多加几个角色挡路得多。

ARTEX 给的是一个能用的 Agent 前端：会话、工具调用、模型切换都是现成的。我接手时的想法很简单，把角色改成 CTF 用的几个，再补几条工具，应该就能跑题了。

跑通一道题确实不难。难的是同时开两条路线之后：附件属于哪一轮，脚本是谁写的，另一个 solver 还在不在跑，最后那句“已完成”又是按什么说的。界面上这些东西全糊在一起。

这不是模型能力问题，是工作台的问题——它没把 Agent 做过的事情留在别人能接的地方。下面记的是为了让这几件事有地方落，我改了哪些结构。

先交代来源。prtseek 基于 RuoJi6/ARTEX 二次开发，原始项目是 Autumn-27/ARTEX，继续用 AGPL-3.0，Go 模块路径也还留着 github.com/Autumn-27/artex。改动集中在 CTF 这个用法上：入口收窄、默认角色换掉，再补会话、协作、验证这几块。

默认的四个角色

triage、command、solver、writeup。名字就是字面意思：先看材料，再拆任务，然后干活，最后整理。

要花心思的是派发时那句任务描述。“研究一下这个压缩包”和“按校验文件验证候选，返回匹配项和校验记录”，给下一个人留下的空间完全不同。前一句它打开文件就开始解释，后一句它知道该在哪停下来核对。

也犯不上为了让四个角色都露脸而轮流说一遍话。材料齐、步骤明确的小题，一个 solver 直接做更快；确实有两条值得分开试的路线，再让 command 并行派。writeup 接在脚本和证据后面写，没验证的地方就空着——一旦把猜测写成定论，后面改回来很费劲。

execution 和 outcome

有个场景我想了很久：任务查完材料，发现缺附件，然后正常结束。界面该显示成功还是失败？只留一个 status，选哪边都少一半信息。

所以现在分开存。execution 记程序状态：跑完了、取消了、超时了。outcome 记目标进度：unverified、partial、blocked、verified。上面那个例子落下来是：

execution = completed
outcome   = blocked
summary   = 缺少题目要求的附件，暂时无法验证

读起来不矛盾：这一轮检查做完了，题还没解出来。

找到像 flag 的字符串也一样，先报 partial，真校验过再改。report_outcome 要求填验收条件、验证方式、证据和产物，至少让“成功”后面跟着点得开的东西。至于那份证据够不够说明答案对，还得看内容——程序查得到一个合法编号，不等于这些编号能说明问题。

会话目录

会话工作目录是这套流程里最实在的单位。附件有地方放，脚本有地方找，WRITEUP 也能挂回同一条记录。前端、SQLite 里的状态和磁盘上的文件得对得上，不然聊得再顺，过几天回来还是不知道哪个文件有用。

子任务有自己的会话和目录，继承父会话实际在用的模型配置。启动时任务文本里带上父会话的材料目录和根会话的题目目录，要求只读引用原材料、产物写进自己的目录。两个 solver 都生成 result.txt 时，至少不会默认落到同一个位置。

“只读”目前只是任务文本里的约定。目录分开不等于权限分开：没有 OS 级隔离，也没有一人一个容器。真要限制文件访问，得往下做到工具执行层，光靠目录名解决不了。

还欠着的

做完的和没做的都记一句。目录只读靠约定；writeup 的质量完全取决于上游证据，证据虚它写出来也虚；四个角色之外没有独立的复核角色，人工检查还是得在会话外面做。

这三条都不算新问题，只是这次没排上。真正改过的还是上面那几处，代码在下面。
