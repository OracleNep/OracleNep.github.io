把 prtseek 改成一个 CTF 工作台

题目附件放哪，派出去的任务怎么收尾，找到的字符串到底算不算答案。这些事比多加几个角色更早需要解决。

给 Agent 一道题，看它调用工具、写脚本，再返回一段答案，整个过程已经很像一个能用的产品了。可只要多追问几轮，或者同时跑两条路线，聊天框里就开始装不下所有事情：附件属于哪一轮，脚本是谁写的，另一个 solver 还在不在跑，最后那句“已完成”又是根据什么说的。

改 prtseek 时，我更关心这些问题。模型已经会读文件和执行工具，工作台还得把它做过的事留下来，让下一步有东西可接。

先交代来源。prtseek 基于 RuoJi6/ARTEX 二次开发，原始项目来自 Autumn-27/ARTEX，继续使用 AGPL-3.0，Go 模块路径也保留着 github.com/Autumn-27/artex。这次工作的重点是把它往 CTF 使用场景收：简化入口，调整默认角色，再补会话、协作和验证中缺少的部分。

四个角色，用不着每次都到齐

现在默认有 triage、command、solver 和 writeup。名字很好理解：triage 先看材料，command 拆任务，solver 执行，writeup 整理结果。真正容易写错的是它们之间的任务描述。

比如一个压缩包里有几个候选字符串，还有一份校验文件。派发“研究一下这个压缩包”，和派发“按校验文件验证候选，返回匹配项及校验记录”，给下一位执行者留下的空间完全不同。前一种很容易读完文件就开始解释；后一种至少知道该在哪里停下来检查。

也没必要为了走完流程，让四个角色轮流说一遍话。材料齐全、步骤明确的小题，直接交给一个 solver 就行。确实有两条值得分别试的路线，再让 command 并行派发。writeup 放在后面接已有的脚本和证据，整理时还没验证的地方就留着，别顺手把猜测写成定论。

“跑完了”这个状态太含糊

一个任务查完材料，发现缺附件，然后正常结束。界面该显示成功还是失败？如果只留一个 status，无论选哪边都少了一半信息。

所以后端分别保存 execution 和 outcome。execution 记录运行结束、取消、超时这些程序状态；outcome 记录目标进度，有 unverified、partial、blocked、verified 四种。上面的缺附件例子就可以记成：

execution = completed
outcome   = blocked
summary   = 缺少题目要求的附件，暂时无法验证

这样看就很清楚了：这一轮检查做完了，题还没解出来。

找到一个像 flag 的字符串也一样。可以先报 partial，等实际校验后再更新。report_outcome 要求把验收条件、验证方式、证据和产物写进去，至少让“成功”后面跟着能打开的东西。至于那份证据是否足够说明答案正确，还得看内容，程序查到一个合法编号就自动盖章显然不够。

材料得有归属

会话工作目录是这套流程里一个很实际的单位。附件进来有地方放，solver 写的脚本有地方找，之后生成的 WRITEUP 也能回到同一条任务记录上。前端、SQLite 里的状态和磁盘上的文件需要对得起来，否则聊得再顺，过几天回来还是不知道哪个文件有用。

子任务会创建自己的会话和目录，继承父会话实际使用的模型配置。启动时，任务文本会带上父会话材料目录和根会话的题目目录，并要求只读引用原材料，把产物写到自己的目录里。这样两个 solver 都生成 result.txt 时，至少不会默认落在同一个位置。

不过这条“只读”目前是任务里的约定。目录分开并没有给工具套上操作系统权限，也没有把每个 solver 放进独立容器。需要文件访问隔离的话，还得继续往工具执行层做，不能在目录名上解决。

我希望后面接手一条会话时，先能找到原题、实际执行过的脚本和验证结果。聊天记录可以很长，但不该只有聊天记录。
